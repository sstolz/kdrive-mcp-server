# BR-310 — CIMD clients at the token endpoint

## Rule

At the token endpoint a CIMD client ID is authenticated with method `none` only: it is presented as `client_id` in the body, without `client_secret` and without Basic, and it is acceptable under BR-305 with the current configuration; otherwise 401 `invalid_client` (BR-136 v2), decided before any code or family is looked up, so no code is consumed and no family is touched. No document is fetched at the token endpoint. `authorization_code` is allowed when the code is bound to that client ID; a code yields a refresh token only when the snapshot bound to it (BR-308) kept `refresh_token`; `refresh_token` is allowed for families of that client ID. The configuration is read at startup, so removing an origin takes effect at the restart that applies it: codes do not survive that restart, and from its first request every refresh token of the origin's clients gets 401 `invalid_client`.

## Rationale

CIMD clients are public clients; refusing before any lookup prevents an unlisted client ID from consuming or probing codes and families, and origin removal is the cut-off (D-4). Source: [F-028 v2](../features/F-028-client-id-metadata-documents.md).

## Examples

- **Given** a CIMD client that completed authorization
  **When** it redeems its code with `client_id` in the body and no secret
  **Then** tokens are issued and the fetch port is not called
- **Given** the same client
  **When** it presents Basic or a body secret
  **Then** 401 `invalid_client`
- **Given** a client ID under an unlisted origin
  **When** it presents a listed client's code or refresh token
  **Then** 401 `invalid_client` and the code and family stores are not read
