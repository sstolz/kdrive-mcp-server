# BR-411 — Repeated consent POST

## Rule

(1) **Record.** When the consent handler takes a live pending consent past every BR-129 check (identifier known and unexpired, no repeated form parameter, cookie match of BR-130, `decision` `approve` or `deny`), it records, under that identifier and before `discover()`, the consent's cookie hash, the `decision`, the consumption time `t0` (the clock read when the identifier was consumed) and the first POST's completion, with the outcome pending. When that first POST answers the decision's 302 (approve: the BR-131 upstream redirect after its flow is stored; deny: the client redirect with `error=access_denied`), the record keeps that response's `Location` and becomes settled. When it ends in anything else (503 `busy`, client redirect `temporarily_unavailable`, or an exception), the record is deleted; the first POST's own answer is unchanged.

(2) **Replay.** A consent POST whose `consent` value is not a pending consent but has a record is eligible when all hold on its arrival: the clock read on arrival is before `t0 + 10` seconds; the form repeats no parameter; its `decision` equals the recorded one; and the request's cookie matches the recorded hash under BR-130 (exactly one well-formed `__Host-kdrive-oauth`, constant-time SHA-256 comparison). The window is checked on arrival only, never again after a wait. An eligible repeat of a settled record is replayed at once. An eligible repeat of a pending record waits on the completion captured from the record on arrival, with no second `discover()` call; the completion is released whatever the first POST's end, an exception included, always resolves (never rejects) and itself carries the outcome (the `Location` or a failure). After the wait the repeat re-reads the BR-299 latch and answers the 503 `busy` page if it is set; otherwise it is replayed if the first POST answered the decision's 302, and gets the 400 `consent` page in every other case. A replay repeats the first answer's headers: status 302, the recorded `Location` byte for byte and `Cache-Control: no-store`; for `approve` also `Set-Cookie` with the bound value taken from the repeat's own cookie and the BR-130 attributes (`Max-Age=600`); for `deny` no `Set-Cookie`. Any number of repeats inside the window is replayed.

(3) **No side effect.** A replay creates, deletes or changes no pending consent, flow, code, client, family or cache, starts no upstream fetch, logs no event, and moves no server-side time: `t0` and the flow's `created` time (BR-142 TTL) stay as they were. A repeat that fails (2) gets the existing 400 `consent` page with its single `consent_refused` event, and the record is left unchanged.

(4) **Unchanged cases.** An unknown identifier, a repeat arriving at or after `t0 + 10` s, another or absent cookie, a different `decision`, and an identifier consumed by a failing first presentation (no record) get the 400 `consent` page as today. A latched store (BR-299) still answers the 503 `busy` page first, on arrival and after a wait.

(5) **Bounds.** Records live in memory only, are never written to the state file (BR-292) and a new instance starts with none. The purge before a write (BR-142 v3) deletes every settled record with `time >= t0 + 10` s; a pending record is never purged nor evicted. At most 1,000 records exist; recording into a full set evicts the oldest settled record in insertion order, or records nothing when all are pending, with no event and no effect on the first POST's answer.

## Rationale

A double click on Approve or Deny posts the consent form twice; the browser aborts the first navigation and the second POST found the identifier consumed, stranding the user on "already used" although the authorization was valid. The owner chose a server-side fix without JavaScript and with the CSP unchanged (F-032 D-1). The upstream flow stays one-use at the callback, so nothing can be authorized twice. Source: [F-032 v1](../features/F-032-repeated-consent-post.md).

## Examples

- **Given** a consent approved at `t0` with cookie C
  **When** the same form is posted again with C at `t0 + 1` s
  **Then** 302 with the same `Location` and the same `Set-Cookie`, one flow, one discovery fetch and no event
- **Given** a consent denied at `t0` with cookie C
  **When** the same form is posted again with C at `t0 + 1` s
  **Then** 302 with the same client `Location` (`error=access_denied`), no `Set-Cookie`, one `consent_refused` event in all
- **Given** an approval at `t0`
  **When** repeats arrive at `t0 + 9.999` s and at `t0 + 10` s
  **Then** the first is replayed and the second gets the 400 `consent` page
- **Given** an approval at `t0` with cookie C
  **When** a repeat inside the window carries another cookie or `decision=deny`
  **Then** the 400 `consent` page, and a later repeat with C is still replayed
- **Given** two approve POSTs of one consent while discovery is held
  **When** the discovery reply fails
  **Then** the first gets the `temporarily_unavailable` client redirect and the second the 400 `consent` page
- **Given** 1,000 settled records inside the window
  **When** a 1,001st is recorded
  **Then** the oldest record's repeat gets the 400 page and the newest is replayed
