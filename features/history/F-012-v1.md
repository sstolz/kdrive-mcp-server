## Business rules

Common definitions:

- **Public URL** `P` is the canonical `publicUrl` of F-002 (no terminal
  slash); its **path** is the URL path of `P`, `/` when empty. In
  authenticated mode the proxy issuer and the audience equal `P` (F-002
  auth matrix, F-010 BR-124), and the path of `P` is never `/` (BR-152).
  `P` has one source, the configuration: the MCP endpoint path, the PRM URL
  and its `resource`, the proxy issuer and the verifier audience all derive
  from it (BR-152, D-17).
- **PRM URL** is `<origin of P>/.well-known/oauth-protected-resource<path of P>`.
- **Request target** is the request-target exactly as `node:http` receives it
  (`IncomingMessage.url`), before any URL parsing or normalization. Its
  **target path** is the part before the first `?`; its **query** is the part
  after it.
- **Header value**: the adapter (BR-170) combines repeated header fields as
  Web `Headers.append` does: values joined with `", "`, `Cookie` values joined
  with `"; "`. Every rule below reads that combined value, so a repeated
  `Host`, `Origin`, `Authorization`, `Mcp-Session-Id` or `Content-Type` fails
  the equality or grammar check of its rule.
- An **HTTP-layer error** is a response with `Content-Type:
  application/json`, `Cache-Control: no-store`, `X-Content-Type-Options:
  nosniff` and body exactly `{"error":"<code>"}`.
- **Identity** is the verifier success identity `(iss, sub)` of F-010 BR-141
  v1; in insecure mode it is the fixed pseudo-identity `("insecure", "local")`.
- A **window** for a key starts at the first counted event while no window is
  open for that key and lasts the stated duration; a request is refused when
  the window already holds the stated count. Refused requests are not counted.
  `Retry-After` is the whole number of seconds, rounded up, until the window
  ends.

- **BR-152** — `createHttpHandler`, and therefore `createHttpServer` and
  `startHttpServer`, raise `HttpStartupError` code `CONFIGURATION_UNSUPPORTED`
  unless the configuration satisfies `isResolvedConfiguration` (F-002 BR-021)
  and its `transport` is `http`. With `insecureNoAuth` true, an `upstream`
  option raises `UPSTREAM_PORT_UNEXPECTED`. With `insecureNoAuth` false, these
  checks run in order: an `oauthMode` other than `proxy` raises
  `OAUTH_MODE_UNSUPPORTED`; a public URL whose path is `/` raises
  `PUBLIC_URL_PATH_REQUIRED` (D-9); an absent `upstream` option raises
  `UPSTREAM_PORT_REQUIRED`. Otherwise the proxy is built with
  `createOAuthProxy` (F-010 BR-124 v1) from an `EffectiveProxyConfig` mapped
  from the configuration only: `publicUrl` and `oauthAudience` are `P`;
  `oauthIssuer`, `oauthAllowedSubjects`, `oauthAllowedEmails`,
  `oauthUpstreamClientId`, `oauthUpstreamClientSecret` (resolved by F-002
  from the inline value or `oauthUpstreamClientSecretFile`), `oauthSigningKey`
  (read by F-002 from `oauthSigningKeyFile`) and `oauthAllowedRedirectUris`
  are the configuration's fields of those names. The proxy receives the
  `upstream` option, the clock, the random source and the logger (BR-167),
  and its `verifier` (BR-141 v1) is used. The handler accepts no other source
  of `P`, the audience, the issuer or the secrets (D-17). An error thrown by
  proxy construction (for example BR-100 v2's validator refusal) propagates.
  Each of these happens before any socket is opened, and the
  `HttpStartupError` messages are fixed strings that echo no configuration
  value. Verified by: AC-01, AC-04.
- **BR-153** — The listener binds the effective `httpHost`/`httpPort` of
  F-002 (default `127.0.0.1:3000`, BR-024 v2). In insecure mode it binds
  literal `127.0.0.1` (BR-025 v2); after `listen` succeeds, an insecure
  listener whose bound address is not `127.0.0.1` is closed and
  `HttpStartupError` `INSECURE_BIND_REFUSED` is raised. A failed `listen`
  raises `HttpStartupError` `LISTEN_FAILED` without the system error text.
  Verified by: AC-02.
- **BR-154** — In authenticated mode the routes are exactly: the MCP endpoint
  at the path of `P` (POST, DELETE); the PRM URL path (GET); each F-010
  `metadataPaths` entry (GET); `<path of P>/oauth/register` (POST),
  `<path of P>/oauth/authorize` (GET), `<path of P>/oauth/consent` (POST),
  `<path of P>/oauth/callback` (GET) and `<path of P>/oauth/token` (POST).
  Routes match the target path byte-exactly, without decoding, dot-segment
  resolution or trailing-slash tolerance; a target path that does not start
  with `/` (absolute-form, `*`) matches no route. Any other path yields
  HTTP-layer error 404 `not_found`; another method on a known path yields 405
  `method_not_allowed` with `Allow` listing the methods above (a GET on the
  MCP endpoint therefore yields 405 with `Allow: POST, DELETE`). `HEAD` is not
  supported. Verified by: AC-03.
- **BR-155** — GET on the PRM URL returns 200 `application/json` with members
  exactly `resource` (`P`, which BR-152 also makes the audience that F-010
  BR-128 and the verifier compare), `authorization_servers` (`[P]`) and
  `bearer_methods_supported` (`["header"]`). Verified by: AC-04.
- **BR-156** — Every request is checked for its `Host` value first after
  BR-169's request-target length check, compared case-insensitively. It passes when it equals the WHATWG URL `host` of `P`
  (default port omitted) or, only when the WHATWG `port` of `P` is empty,
  `<hostname of P>:<default port of P's scheme>`; in insecure mode the same
  forms with hostname `localhost` also pass. When `P` has an explicit port,
  the default-port form does not pass. An
  absent `Host`, an empty one or any other value (including a repeated `Host`)
  yields HTTP-layer error 403 `invalid_host` before any routing,
  authentication or body read. Verified by: AC-05.
- **BR-157** — On the MCP endpoint, a request carrying `Origin` is refused
  with HTTP-layer error 403 `invalid_origin` unless the value equals the
  origin of `P` exactly (insecure mode: or that origin with hostname
  `localhost`). On `/oauth/consent` the same rule applies, except that the
  value `null` also passes (D-15). A request without `Origin` passes. The
  check runs after routing and before authentication. Other routes ignore
  `Origin`. Verified by: AC-05.
- **BR-158** — An MCP request's credential comes only from the `Authorization`
  header. An `access_token` query parameter yields 400 HTTP-layer error
  `invalid_request` with `WWW-Authenticate: Bearer error="invalid_request",
  resource_metadata="<PRM URL>"`, whatever the header. Otherwise, no
  `Authorization` value, or one whose scheme is not `Bearer`
  (case-insensitive), yields 401 HTTP-layer error `unauthorized` with
  `WWW-Authenticate: Bearer resource_metadata="<PRM URL>"`. A `Bearer` value
  that does not match `Bearer 1*SP b64token` (RFC 6750 §2.1; this includes a
  repeated `Authorization` header, since `,` and space are outside `b64token`)
  yields the 400 above. A token longer than 4,096 bytes yields the 401 of
  BR-159 without calling the verifier. Verified by: AC-06.
- **BR-159** — Every MCP request, including those carrying a session ID, is
  verified with the F-010 verifier at the injected clock's current time. A
  401 result (F-008 BR-098 v1, BR-099 v1, F-010 BR-141 v1: malformed,
  algorithm, signature, issuer, audience, expired, not yet valid, ID token)
  yields 401 HTTP-layer error `invalid_token` with `WWW-Authenticate: Bearer
  error="invalid_token", resource_metadata="<PRM URL>"`. A 403 `identity`
  result (BR-100 v2) yields 403 HTTP-layer error `access_denied` without
  `WWW-Authenticate`. No response distinguishes rejection reasons, and no
  `error_description` is sent. Verified by: AC-07, AC-08.
- **BR-160** — Body limits are 262,144 bytes for POST on the MCP endpoint and
  32,768 bytes for `/oauth/register`, `/oauth/consent` and `/oauth/token`;
  every other route and method, including GET and DELETE on any route,
  accepts no body: a nonzero `Content-Length` or any `Transfer-Encoding`
  field yields 413 at the body-framing step, without reading the body,
  and the connection is closed. A `Content-Length` above the limit yields
  HTTP-layer error 413 `payload_too_large` before authentication and without
  reading the body; a body that exceeds the limit while being read yields the
  same 413, stops reading and closes the connection. For POST requests: a
  `Content-Encoding` other than absent or `identity` yields 415
  `unsupported_media_type`; the media type (parameters ignored, case-insensitive) must be `application/json`
  on the MCP endpoint and `/oauth/register`, and
  `application/x-www-form-urlencoded` on `/oauth/consent` and `/oauth/token`,
  else 415 `unsupported_media_type`; a body that is not valid UTF-8, an MCP
  body that is not valid JSON, or an MCP body whose top-level value is an
  array (a JSON-RPC batch, D-10) yields 400 `invalid_request`, so each MCP
  request carries one JSON-RPC message. On the MCP endpoint these checks run
  after authentication (BR-158/BR-159) except the body-framing checks
  (`Content-Length`, `Transfer-Encoding`). The router reads the body itself
  and gives the SDK transport the parsed JSON as `parsedBody`, so the SDK's own
  `maxRequestBodySize` does not apply and 262,144 bytes is the only MCP body
  limit. Verified by: AC-09.
- **BR-161** — Authenticated MCP requests are limited per identity to 120 per
  60-second window. A refused request yields HTTP-layer error 429
  `rate_limited` with `Retry-After`, after authentication and before any body
  read. Verified by: AC-10.
- **BR-162** — Process-wide windows, keyed by route, bound unauthenticated
  OAuth work: `/oauth/register` 30 per 3,600 seconds; `/oauth/authorize`,
  `/oauth/consent` and `/oauth/callback` 30 per 60 seconds each;
  `/oauth/token` 60 per 60 seconds. A request on these routes is counted and
  checked before its body is read; refusal is HTTP-layer error 429
  `rate_limited` with `Retry-After`. MCP requests have no process-wide window:
  a request whose token verifies is never refused by one (D-7). Verified by:
  AC-11.
- **BR-163** — An MCP POST without `Mcp-Session-Id` whose body is a single
  JSON-RPC request with method `initialize` creates a transport with a
  `sessionIdGenerator` returning 32 random bytes base64url (43 characters),
  `enableJsonResponse: true` and no `eventStore`, and a new `McpServer` from
  `createNavigationServer` (BR-059 v2) with the injected configuration and
  dependencies. The session is registered, bound to the request's identity,
  only when the transport reports the issued ID through
  `onsessioninitialized`; when no ID is issued, the transport and the server
  are closed and nothing is registered. The router's `onsessioninitialized`
  callback never throws: it catches any exception raised while registering
  (including by the logger's `session_opened` call) and records a failure;
  after `handleRequest` returns, a recorded failure discards the SDK's
  response, closes the transport and the server, leaves nothing registered,
  releases the creation slot (BR-164) and yields HTTP-layer error 500
  `server_error`. Without `Mcp-Session-Id`, any other body (including a
  2026-07-28 `server/discover` probe, D-14) yields 400 `invalid_request` and
  creates nothing. A request whose `Mcp-Session-Id` is repeated, does not
  match the 43-character grammar, is unknown, expired, or bound to another
  identity yields HTTP-layer error 404 `session_not_found`, identical in all
  these cases. A DELETE without `Mcp-Session-Id` yields 400
  `invalid_request` and closes nothing. A DELETE by the bound identity closes
  the session. MCP responses that carry a body are JSON (`Content-Type:
  application/json`), never an SSE stream; a POST whose message is a
  notification or a JSON-RPC response gets the SDK's 202 without a body. The
  SDK transport sets `Mcp-Session-Id` on each JSON response that answers a
  JSON-RPC request within a session, including the `initialize` response; its
  202 and its transport-level error responses carry none. Verified by: AC-12, AC-13, AC-15, AC-22.
- **BR-164** — A session closes after 1,800 seconds without a request bound
  to it or 86,400 seconds after creation, whichever comes first; expired
  sessions are closed before each session lookup or creation. Each identity
  holds at most 8 sessions: when a ninth registers, that identity's session
  with the oldest last request is closed. The process holds at most 64
  sessions, counting creations in progress: an `initialize` beyond that,
  after closing expired ones, yields HTTP-layer error 503
  `temporarily_unavailable` with `Retry-After: 60` before anything is
  created. Closing a session closes its transport and its `McpServer`; its ID
  then yields 404 (BR-163). A request bound to a session that closes, for any
  reason, while the request is in flight (other than the DELETE that closes
  it) is answered with HTTP-layer error 503 `temporarily_unavailable` without
  `Retry-After`, and the result of its call is discarded; the router does not
  wait on the SDK transport, which never settles such a request after
  `close()` (D-18). Verified by: AC-14, AC-19.
- **BR-165** — OAuth routes call the F-010 handlers as in F-010 Contract
  details: `query` is the query parsed as `URLSearchParams`, `form` is the
  body parsed as `application/x-www-form-urlencoded`, `body` is the body text,
  `cookie` is the `Cookie` value when present and `authorization` is the
  `Authorization` value when present (both as combined by BR-170). The
  handler's status, headers (including every `Set-Cookie` and
  `WWW-Authenticate`) and body are sent unchanged. A handler that throws
  yields the 500 of BR-170. Verified by: AC-15.
- **BR-166** — The request given to the SDK transport carries no
  `Authorization` or `Cookie` header, and `handleRequest` receives no
  `authInfo`. No tool handler, `PolicyDependencies` call, `McpServer` or the
  F-010 upstream port receives a client bearer token; MCP requests make no
  upstream call. Verified by: AC-16.
- **BR-167** — No HTTP response header or body, error message or logger call
  produced by this feature contains a client bearer token, the kDrive
  credential, the upstream client secret, signing-key material, an upstream
  token, a session ID (except in the `Mcp-Session-Id` header of a response to
  a request within that session, including the one that creates it) or an
  identity value. The optional logger is also
  given to `createOAuthProxy`, so it receives the BR-143 events with their
  fields; the only events this feature adds are `request_refused` (fields:
  `route`, one of `mcp`, `prm`, `as_metadata`, `register`, `authorize`,
  `consent`, `callback`, `token` or `unknown`; `status`; `error` code),
  `session_opened` (`count`; `requested_protocol`, the `initialize`
  `params.protocolVersion` when it matches `^\d{4}-\d{2}-\d{2}$`, else
  `other`) and `session_closed` (`reason`: `deleted`, `idle`, `lifetime`,
  `evicted` or `shutdown`; `count`). Each HTTP-layer error response this
  feature sends (every row of the Contract details status table, including
  BR-164's 503 and BR-170's 500) emits exactly one `request_refused`, whose
  `status` and `error` are that response's; `route` names the route whose
  path the target path matches byte-exactly (BR-154), else `unknown`.
  Responses produced by the SDK transport or an F-010 handler emit none.
  `session_opened` is emitted once per registered session and
  `session_closed` once per closed session; `count` is the number of
  registered sessions after that change. Verified by: AC-14, AC-17, AC-19.
- **BR-168** — In insecure mode only the MCP endpoint exists, at the path of
  `P` (`/` for the origin BR-025 v2 derives, or the path of an explicit
  `http://127.0.0.1:<port>/<path>` public URL); OAuth and PRM paths yield 404. No credential is
  required or verified; an `Authorization` header is ignored and stripped
  (BR-166). The pseudo-identity is used for BR-161, BR-163 and BR-164.
  Verified by: AC-18.
- **BR-169** — The `node:http` server uses `requireHostHeader` false (so
  BR-156 answers a request without `Host`), `headersTimeout` 10,000 ms,
  `requestTimeout` 30,000 ms, `keepAliveTimeout` 5,000 ms, `maxHeaderSize`
  16,384 bytes and `maxConnections` 256. A request target longer than 8,192
  bytes yields HTTP-layer error 414 `invalid_request` before the `Host`
  check. `close()` runs in this order: (1) it stops accepting connections;
  (2) it closes every session (reason `shutdown`), which settles their
  in-flight requests with BR-164's 503; (3) it waits until the adapter has
  finished writing each response settled in step 2, or 1,000 ms, whichever
  comes first; (4) it ends every remaining connection
  (`closeAllConnections`); (5) it resolves once the listener is closed. From
  step 1 on, `handle()` answers every new request with HTTP-layer error 503
  `temporarily_unavailable` without `Retry-After` and creates nothing, and
  an `initialize` already in flight when step 1 starts registers no session:
  its `onsessioninitialized` callback closes that transport and server and
  its request gets BR-164's 503. A response settled after step 2 may be cut
  by step 4; this is accepted (process shutdown).
  Verified by: AC-19.
- **BR-170** — The `node:http` adapter turns each incoming request into a Web
  `Request` (method as received; headers built by appending every field of
  `rawHeaders` in order; body streamed from the socket, except for GET and
  HEAD, whose `Request` has no body because a Web `Request` cannot carry one
  (BR-160 refuses their framing); a fixed placeholder
  URL that the router never reads) and calls `handle(request, target)` with
  the raw request target. It writes the response status, headers (each
  `Set-Cookie` as its own field) and body unchanged. Any exception thrown in
  the request path (the adapter, the router, an F-010 handler,
  `createNavigationServer` or the SDK transport) yields HTTP-layer error 500
  `server_error` when no response has started (otherwise the connection is
  closed), carries nothing of the error, and later requests are still
  served. When the adapter writes a response while the request body has not
  been fully received (`IncomingMessage.complete` is false), the response
  carries `Connection: close` and the adapter ends the connection after
  writing it, so the connection is not kept alive to drain an unread body.
  Verified by: AC-03, AC-05,
  AC-09, AC-15, AC-19.
- **BR-171** — The acceptance composition `scripts/http-acceptance.ts`, run by
  `make http-acceptance` in the dev Compose service: (1) serves
  authenticated proxy mode through `startHttpServer` with the real upstream
  OIDC port and, as navigation dependencies, a synthetic in-memory drive and
  resolver, with a fixed synthetic placeholder in place of the kDrive
  credential and no kDrive call; (2) obtains the upstream client secret and
  the signing key only through F-002's `oauthUpstreamClientSecretFile` and
  `oauthSigningKeyFile`, and refuses to start, with a fixed message, when
  `oauthUpstreamClientSecret` is supplied inline; (3) is started by a Make
  recipe that publishes its port on the host's `127.0.0.1` only; (4) writes
  each BR-167 and BR-143 logger event as one JSON line `{"event":<name>,
  ...fields}` to stderr; (5) is absent from the published package. The CLI is
  unchanged. Verified by: AC-23.

## Contract details

```ts
createHttpHandler(options: {
  configuration: ResolvedConfiguration;   // transport http
  dependencies: PolicyDependencies;       // F-005 navigation dependencies
  upstream?: UpstreamOidcPort;            // required when authenticated, refused when insecure (BR-152)
  clock: () => Date;
  randomBytes: (size: number) => Uint8Array;
  logger?: { event(name: HttpEvent | ProxyEvent, fields: Record<string, string | number>): void };
}) -> { handle(request: Request, target: string): Promise<Response>; close(): Promise<void> }

type ListenPort = (server: import("node:http").Server, port: number, host: string) => Promise<AddressInfo>;
createHttpServer(options) -> { server: import("node:http").Server; close(): Promise<void> }
startHttpServer(options & { listen?: ListenPort }) -> Promise<{ address: AddressInfo; close(): Promise<void> }>
```

`createHttpHandler` performs no I/O while constructing and builds the
`EffectiveProxyConfig` itself (BR-152). `createHttpServer` never listens;
socket tests call `server.listen(0, "127.0.0.1")` on the server it returns.
`startHttpServer` builds the server with `createHttpServer`, listens through
`listen` (default `server.listen(port, host)`) on the effective host and port
of BR-153, and applies BR-153's post-listen guard; tests inject `listen` to
observe its arguments and to feed that guard.

`HttpStartupError` codes: `CONFIGURATION_UNSUPPORTED`,
`UPSTREAM_PORT_UNEXPECTED`, `OAUTH_MODE_UNSUPPORTED`,
`PUBLIC_URL_PATH_REQUIRED`, `UPSTREAM_PORT_REQUIRED` (BR-152),
`INSECURE_BIND_REFUSED`, `LISTEN_FAILED` (BR-153).

| Status | Code | Raised by |
| --- | --- | --- |
| 400 | `invalid_request` | BR-158, BR-160, BR-163 |
| 401 | `unauthorized`, `invalid_token` | BR-158, BR-159 |
| 403 | `invalid_host`, `invalid_origin`, `access_denied` | BR-156, BR-157, BR-159 |
| 404 | `not_found`, `session_not_found` | BR-154, BR-163 |
| 405 | `method_not_allowed` | BR-154 |
| 413 | `payload_too_large` | BR-160 |
| 414 | `invalid_request` | BR-169 |
| 415 | `unsupported_media_type` | BR-160 |
| 429 | `rate_limited` | BR-161, BR-162 |
| 500 | `server_error` | BR-163, BR-170 |
| 503 | `temporarily_unavailable` | BR-164, BR-169 |

MCP endpoint order: target length (BR-169) → Host (BR-156) → route and method
(BR-154) → body framing (BR-160) → Origin (BR-157) → credential and
verification (BR-158, BR-159; skipped in insecure mode) → identity window
(BR-161) → encoding, media type, body and JSON (BR-160) → session (BR-163,
BR-164) → SDK transport. OAuth route order: target length → Host → route and
method → body framing → Origin (`/oauth/consent` only) → route window
(BR-162) → encoding, media type and body → F-010 handler. Responses produced
by the SDK transport (for example 406, or 400 for an unsupported
`MCP-Protocol-Version`) are passed through.

## Decisions

- **D-1 — Proxy mode only** (owner decision 1). Rejected: implementing
  `delegate`/`delegate-static` with JWKS fetching now (no qualified provider
  could use it; untestable against a real provider).
- **D-2 — `node:http` plus the SDK Web-standard transport.** The SDK 2.4.0
  transport implements Streamable HTTP sessions and JSON-RPC handling; a small
  router in front owns Host, Origin, auth, limits and session binding, which
  the SDK leaves to external middleware (its own options are deprecated).
  Rejected: an HTTP framework (new dependency for a fixed route table);
  re-implementing Streamable HTTP (protocol drift); the SDK
  `createMcpHandler`/bearer helpers (expect an `AuthInfo` with the raw token,
  conflicting with BR-166, and do not bind sessions to subjects).
- **D-3 — One `McpServer` per session.** The SDK transport binds one server;
  per-session servers keep F-006 opaque continuation handles session-bound.
  Rejected: one shared server (handles would cross sessions and identities).
- **D-4 — JSON responses and no standalone GET stream.** The tools are
  request/response and send no server-initiated messages; GET returns 405 as
  Streamable HTTP permits, and the transport is built with
  `enableJsonResponse: true` and no `eventStore` (BR-163). This avoids
  long-lived connections and keeps the limits simple. Rejected: SSE streams
  (open connections outlive request timeouts, more DoS surface, no benefit
  today).
- **D-5 — 404 for every session mismatch.** A foreign session ID behaves like
  an unknown one, so session IDs cannot be probed and clients re-initialize.
  Rejected: 403 for a foreign session (reveals that the ID exists).
- **D-6 — 403 for a denied identity without a challenge.** A denial is not a
  scope problem; `insufficient_scope` would trigger MCP step-up authorization
  loops. Rejected: 401 (would loop through login); `insufficient_scope`.
- **D-7 — Process-wide windows for OAuth routes only.** Behind a reverse
  proxy the peer address is the proxy's, and trusting `X-Forwarded-For`
  needs configuration that does not exist. The bounds keep F-010 stores below
  capacity: 30 authorize or consent requests per minute create at most 300
  pending entries per 600 seconds (store bound 1,000), and 30 registrations
  per hour need over 33 hours to cycle 1,000 clients. Residual risk: an
  attacker who sustains more than the window's count (for example one
  registration every 2 minutes, or 61 token requests per minute) keeps that
  route closed to the owner for as long as it sustains them; registration
  after a restart and token refresh are then blocked. Accepted for a
  single-owner v1; `docs/oauth-proxy.md` records it and recommends
  per-client-IP limits at the reverse proxy. The same residual applies to
  the connection cap: an unauthenticated client holding 256 connections
  (`maxConnections`, BR-169) within the header and request timeouts keeps
  new connections out for as long as it sustains them; the reverse proxy's
  per-client-IP connection limits are the documented mitigation. MCP requests get no
  pre-verification window: one ES256 check on a token of at most 4,096 bytes
  is already bounded by `maxConnections`, the timeouts and the header caps,
  and a failure window would let junk traffic deny the owner's valid tokens.
  Rejected: per-IP limits in process (meaningless behind the proxy); no
  limits (F-010 D-14 residual risk); an MCP failure window refusing before
  verification (sustained lockout of authenticated traffic).
- **D-8 — No TLS, CORS or forwarded headers in process.** SPEC §9 places the
  server behind a reverse proxy; Claude clients call from servers, not
  browsers. Rejected: CORS (widens cross-origin access with no matrix need).
- **D-9 — Audience equals the MCP endpoint URL, which has a path.** MCP
  clients send the server URL as `resource` and F-010 BR-128 compares it
  byte-exactly with the audience, so the endpoint is served at the path of
  `P`. With an origin-only `P`, a client that serializes the URL with a
  trailing slash would receive `invalid_target` after the whole login, so
  authenticated startup refuses it (`PUBLIC_URL_PATH_REQUIRED`, BR-152).
  Insecure mode compares no audience, so its `P` may be the origin F-002
  derives or an explicit `http://127.0.0.1:<port>/<path>`; the endpoint sits
  at the path of `P` either way (BR-168). Rejected: a fixed `/mcp` suffix appended to `P` (audience would
  differ from the endpoint URL); accepting an origin-only `P` with a
  documentation warning (fails late and opaquely).
- **D-10 — Limits.** 120 requests per minute per identity covers interactive
  use (a few calls per prompt) while bounding a runaway agent; 262,144 bytes
  is far above any tool argument of F-005–F-009; 32,768 bytes leaves F-010
  BR-127's 16,384-byte check reachable with a 400; 8 sessions per identity
  covers several clients and reconnections, 64 overall bounds memory; 30
  minutes idle matches interactive gaps; 24 hours caps a session's life.
  `keepAliveTimeout` 5,000 ms is Node's default; `headersTimeout` and
  `requestTimeout` tighten Node's defaults (60,000 and 300,000 ms). A reverse
  proxy that keeps idle upstream connections open longer than 5 seconds can
  reuse a socket Node has just closed and return an intermittent 502, so
  `docs/oauth-proxy.md` requires its upstream idle timeout to be below 5
  seconds. JSON-RPC batches are refused (BR-160) so that BR-161 counts
  messages: the SDK accepts arrays of up to 100 messages, which would
  multiply the per-identity limit a hundredfold, and the MCP 2025-06-18
  revision removed batching. Rejected: unbounded sessions; refusing a ninth
  session (would lock a reconnecting client out until the idle timeout);
  raising `keepAliveTimeout` above common proxy idle timeouts (idle sockets
  would hold `maxConnections` slots longer); counting each batch message
  against BR-161 (accepts a construct the served protocol versions no longer
  define).
- **D-11 — Credential only in the header; no token to tools.** MCP
  authorization forbids tokens in query strings and token passthrough; tools
  never need the client token because kDrive calls use the server's own
  credential. Rejected: passing `AuthInfo` to handlers (no consumer, leak
  surface).
- **D-12 — BR-025 v2.** The insecure switch now enables a real listener; its
  loopback guarantee is kept and enforced again after `listen`. Rejected:
  leaving BR-025 v1's "cannot enable an implemented listener" in force (would
  forbid the ticket's insecure switch).
- **D-13 — AC-21 runs an acceptance composition** (owner decision, 2026-11-03).
  `make http-acceptance` runs `scripts/http-acceptance.ts` in the dev Compose
  service (BR-171): the real HTTP layer and the real proxy with the
  Infomaniak upstream, and the navigation server over a synthetic in-memory
  drive and resolver; no kDrive credential is used, and the CLI keeps its
  "runtime not implemented" diagnostic. The container listens on the
  configured `httpHost` (`0.0.0.0` inside its own network namespace) and the
  recipe publishes the port on the host's `127.0.0.1` only, where the owner's
  HTTPS reverse proxy or tunnel connects; this is a `compose run` argument,
  not a Docker engine or socket change, and the production image is
  untouched. Secrets live in owner-provisioned files under the git-ignored
  `secrets/` directory, read through F-002's `*File` settings. The script sits
  outside `src/`, so `tsconfig.build.json` does not compile it and the
  package allowlist (`dist/`, `LICENSE`, `NOTICE`, `README.md`) excludes it.
  Rejected: deferring AC-21 until #6/#7 (blocks #12 closure on unrelated
  work); a `--http` CLI mode whose tools all fail (adds a production branch
  that pretends to serve kDrive and evidences only `tools/list`); a
  persistent Compose service with a port publication (exposes a port for
  every `compose up`).
- **D-14 — Serve only the 2025-era sessionful protocol in v1.** The
  compatibility matrix records authorization version 2025-11-25 for
  claude.ai, Claude Desktop and Claude iOS; SDK 2.4.0 clients default to
  `legacy` negotiation, and in `auto` mode they fall back to `initialize`
  when the `server/discover` probe gets an HTTP 4xx other than 401/403 whose
  body is not JSON-RPC (`classifyHttpError` in the client bundle). The 2026
  era has no `Mcp-Session-Id` sessions, so D-3's per-session binding of F-006
  continuation handles would need a new design. A sessionless non-initialize
  POST therefore gets BR-163's 400. AC-21 records the version Claude requests
  (`requested_protocol`); if a target client needs 2026-07-28, a follow-up
  ticket adds a modern leg. This is reversible and additive, so it is not an
  owner question. Rejected: a modern leg routed by `isLegacyRequest` in front
  of `createMcpHandler({ legacy: 'reject' })` (second serving path and handle
  redesign with no client in the matrix needing it); answering
  envelope-carrying requests with the SDK's `-32022` unsupported-version
  error (puts the modern entry in the request path only to produce an error;
  negotiating SDK clients already fall back on the 400). Residual: a client
  pinned to 2026-07-28 cannot connect.
- **D-15 — `Origin: null` passes on `/oauth/consent`.** F-010 BR-129 sends the
  consent page with `Referrer-Policy: no-referrer`; under the Fetch standard
  a non-GET form submission from such a page carries `Origin: null`, so
  refusing `null` would refuse every real consent. CSRF protection on that
  route comes from F-010 BR-129/BR-130: a one-use consent ID bound to the
  `SameSite=Lax` `__Host-kdrive-oauth` cookie, which a cross-site POST does
  not carry. The MCP endpoint still refuses `null`. Rejected: changing the
  F-010 referrer policy (needs a new F-010 version and would leak the consent
  URL as referrer); dropping the Origin check on consent (loses the
  foreign-origin refusal for no gain).
- **D-16 — Raw request data at the adapter.** Node's `req.headers` keeps only
  the first `Host` and `Authorization`, Web `Headers` joins `Cookie`, and
  WHATWG URL parsing resolves dot segments and `\`. The adapter therefore
  builds headers from `rawHeaders` with `Headers.append` and passes the raw
  target (BR-170); singleton checks then fail on the combined value with the
  rule's own error, and `requireHostHeader: false` lets BR-156 answer a
  missing `Host`. A joined `Cookie` is legitimate (RFC 9113 §8.2.3 lets
  HTTP/2 split cookies), so a repeated `Cookie` is not refused. Rejected: a
  header-count map passed to `handle` (a second representation of the same
  data); accepting Node's plain 400 for a missing `Host` (contradicts
  BR-156's error shape).
- **D-17 — One source for `P`, the audience and the secrets.** The handler
  receives the configuration and only the upstream OIDC port, and maps the
  `EffectiveProxyConfig` from the configuration itself (BR-152), so the PRM
  `resource`, the endpoint path, the proxy issuer and the verifier audience
  cannot diverge, and the secrets come only from F-002's resolution. An
  `upstream` passed in insecure mode is refused rather than ignored, so a
  composition that believes it is authenticated fails at startup. Rejected:
  injecting a separate `EffectiveProxyConfig` (a second source for `P` and
  the audience, which breaks the audience binding D-9 relies on); ignoring
  an insecure-mode `upstream` (silent misconfiguration).
- **D-18 — In-flight requests on a closing session get 503.** SDK 2.4.0's
  `close()` drops each pending JSON response without settling it, and a later
  `send()` throws, so a request in flight when its session closes (DELETE,
  idle or lifetime expiry, eviction, shutdown) would never be answered and
  would hold its socket and a `maxConnections` slot. The router therefore
  settles it with 503 `temporarily_unavailable` (BR-164), and the server's
  `close()` ends the remaining connections (BR-169) because Node's
  `server.close()` waits for active ones. Because the adapter writes those
  503s asynchronously, `close()` first waits until they are written, bounded
  by 1,000 ms, so that `closeAllConnections` cannot destroy a socket before
  its 503 reaches the wire. Rejected: waiting on the SDK
  promise (never settles); closing the connection without a response (a
  client cannot tell it from a network failure); a shutdown grace period for
  in-flight calls (more lifecycle state for a single-owner v1; the client
  receives a 503 and can retry); an unbounded write drain (a client that
  stops reading could hold shutdown open).
- **D-19 — BR-059 v2: one navigation factory for both transports.** Each HTTP
  session needs its own `McpServer` (D-3) with the same tools and policy as
  stdio, so `createNavigationServer` accepts an HTTP preflight object and the
  stdio-only check moves to the stdio runner, which keeps refusing HTTP
  configuration; BR-152 already refuses a stdio configuration on the HTTP
  side. The rule's purpose (construction only from a proved preflight object
  and trusted dependencies, without I/O) is kept, so BR-059 keeps its ID and
  goes to v2 (AGENTS.md §7). Rejected: a separate HTTP factory sharing the
  tool registration (a second construction path, and F-005's "rejects HTTP
  configuration" would still need a new version); passing the HTTP layer a
  copied configuration with `transport: stdio` (forbidden by BR-059's exact
  preflight object and BR-021).
