## Rule

v2 (F-028 v2, #3, pending acceptance; v1 stays the accepted rule until then): a CIMD client ID is authenticated under BR-310; registered clients are unchanged.

The token handler takes the `Authorization` header and the form parameters. Basic credentials are Base64-decoded, split at the first `:` and each part form-urlencoded-decoded (RFC 6749 §2.3.1). A repeated parameter, Basic together with a body `client_secret`, Basic together with a body `client_id` that differs from the Basic one, a malformed Basic header, or no client identification yields 400 `{"error":"invalid_request"}`. An unknown `client_id`, a method different from the registered one, or a wrong secret (SHA-256 compared in constant time) yields 401 `{"error":"invalid_client"}`, with `WWW-Authenticate: Basic realm="oauth-token"` when the request used Basic. An absent `grant_type` yields 400 `invalid_request`; a `grant_type` other than `authorization_code` or `refresh_token` yields 400 `unsupported_grant_type`; a grant type not registered for the client yields 400 `unauthorized_client`. These checks never read or consume a code or refresh token. Every token response carries `Cache-Control: no-store` and `Pragma: no-cache`, and every error body is exactly `{"error":"<code>"}`.

## Rationale

Clients are authenticated with their registered method before any grant is evaluated; unknown clients re-register after a restart. Source: [F-010 v1](../features/F-010-oauth-proxy.md), AC-17.

## Examples

- **Given** an unknown `client_id`
  **When** a token request arrives
  **Then** 401 `invalid_client`.
- **Given** Basic credentials and a body `client_secret`
  **When** a token request arrives
  **Then** 400 `invalid_request` and the code still redeems later.
- **Given** a CIMD client ID
  **When** it authenticates at the token endpoint
  **Then** it is authenticated under BR-310 (method `none` only); registered clients are unchanged (v2)
