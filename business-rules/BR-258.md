## Rule

The navigation controller exposes `mutate(tool, operation, identity, signal, payload?)`, the only entry point for a gate run: it runs the gate inside `perform` with `paged:false`, answers `SERVER_BUSY` with zero records when another invocation is active, and returns the gate result (BR-255) as its value. When a gate run executes through the policy `execute` dependency inside that invocation, the navigation 10,000 ms deadline, cancellation, session close, dependency-call cap and output checks apply only until the gate starts the intent append. From then on the navigation controller does not abort, race, time out or discard the `execute` call, and the caller receives the gate result (BR-255), never a navigation `REQUEST_TIMEOUT`, `ACCESS_DENIED` or `LIMIT_EXCEEDED` code; the navigation abort signal reaches the gate only as a BR-250 cancellation; a gate result whose serialization exceeds the navigation output bound is returned without its `value` member; and the navigation slot stays held (other calls get `SERVER_BUSY`) until the gate result is returned. After a client cancellation the MCP response may be dropped (MCP cancellation semantics); the audit outcome is then the authority.

## Rationale

A navigation timeout must never report a performed write as failed (D-16-13). Source: [F-016 v1](../features/F-016-mutation-audit-gate.md).

## Examples

- **Given** a mutator answering 200 after 12,000 ms
  **When** `mutate` runs
  **Then** the caller gets `succeeded` and a concurrent read gets `SERVER_BUSY` meanwhile
- **Given** the navigation deadline firing before the intent append
  **When** `mutate` runs
  **Then** the caller gets `REQUEST_TIMEOUT` with zero records
