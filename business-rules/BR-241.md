## Rule

**v1 (active until v2 acceptance)**

Any write error, short write, `fdatasync` error or stream `error` event latches the sink as failed for the process lifetime; every later append rejects without I/O. An oversize record (BR-236) does not latch the sink.

**v2 (F-039 v1, #47 lot C, pending acceptance; v1 stays the active rule until then)** — Any write error, short write, fdatasync error, stream error event or BR-259 v2 append timeout permanently latches the sink for the process lifetime and rejects all pending and queued appends with AuditUnavailable (fixed message AUDIT_UNAVAILABLE), without waiting for a write callback. Every later append rejects without I/O or waiting for the old tail. A late success never clears the latch; repeated/late errors are contained. Oversize validation alone still does not latch an otherwise healthy sink. BR-254 v2 close expiry or release error also latches it. Every first latch, including intent/denied timeout and idle/close failures, notifies one shared gate diagnostic path that offers the fixed line `Audit outcome could not be recorded; further writes are refused until restart.\n` to stderr once per gate. Outcome failure shares that once guard; set it before writing to prevent reentrant retries. No error, stack, path, record or secret is included. The diagnostic is separate from audit I/O, never awaited or retried, and its throw, callback failure or stream error cannot change results or retain shutdown. Healthy close and oversize-only rejection emit none.

## Rationale

After a failed write the trail can no longer be trusted, so later writes are refused (D-16-1). Source: [F-016 v1](../features/F-016-mutation-audit-gate.md).

Pending v2: Latching future writes is insufficient if a callback-less error leaves the current mutation blocked; uncertain bytes must never be followed by new audit writes. Source: [F-039 v1](../features/F-039-bounded-audit-sink.md).

## Examples

- **Given** a write failing with `ENOSPC`
  **When** an append runs
  **Then** it rejects and the next append rejects without a write call
- **Given** an oversize record
  **When** its append rejects
  **Then** the next normal append succeeds

Pending v2 examples (the accepted examples above remain historical/current as labelled):

- **Given** one pending stderr append and two queued appends
  **When** a stream error fires at 100 ms without a callback
  **Then** all three reject immediately, only one write has started, and every future append rejects without I/O. Maps to `TestBR241_v2_AC02_stream_error_rejects_active_queued_and_future_appends`.
- **Given** an idle stream
  **When** an error fires before any append
  **Then** the sink latches and the next append rejects with zero writes. Maps to `TestBR241_v2_AC02_stream_error_rejects_active_queued_and_future_appends`.
- **Given** a healthy sink and a record of 8,193 bytes including LF
  **When** append validates it
  **Then** it rejects without I/O or latching and the next 8,192-byte record succeeds. Maps to `TestBR241_v2_AC10_validation_and_file_failure_controls`.
- **Given** a real sink/gate composition and an intent/denied timeout, outcome failure, idle error, close expiry or release rejection
  **When** the sink first latches and later errors or outcome handling recur
  **Then** the same fixed diagnostic is offered once in total, without secrets, retries, result changes or callback waits. Maps to `TestBR241_v2_AC14_every_first_latch_offers_one_fixed_diagnostic`.
