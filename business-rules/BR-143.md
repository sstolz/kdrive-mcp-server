## Rule

**v5 (F-052 v1, #72; pending acceptance).** Each refusal caused by a full consent, flow or code store has a whole log delta of exactly one `store_full` event, with only `store` and `count` naming the saturated store and its live count, without `handler`. The handler-level event is removed, not renamed. This supersedes F-028's "today's" consent-store-full row and handler requirement for that refusal under BR-394 v1–v2 (via F-028 Contract details); other authorization-refusal events are unchanged. Each client or family eviction continues to emit exactly one `store_full` event with only `{store, count}` naming that store and its live count at capacity.

The previous version otherwise holds. Its accepted text is preserved below;
acceptance of that text does not establish acceptance of v5.

v3 (F-028 v2, #3; accepted on main `aa540d4`; superseded by v4): the events and the `reason` field of BR-394.

The optional logger receives only a fixed event name from the list in Contract details and fields limited to: handler name, OAuth error code, HTTP status, store name and count. No handler response, error page, thrown error message or logger call contains a client secret, upstream secret, authorization code, PKCE verifier, `nonce`, upstream `state`, client `state`, cookie value, access, refresh or ID token, `client_id`, identity value or signing-key material, except the response that issues that value to its holder (registration response, consent page, code redirect, token response, upstream redirect `state`/`nonce`/challenge, `Set-Cookie`, and the client redirect's echoed `state`).

Version 2 (F-019 v1, #103; accepted on main `68209fe`, 2026-11-11; superseded by v3): the event list adds BR-312's events and the field list adds `clients` and `families`.

**v4 (F-031 v1, #31; accepted on main `901f7af`)** — v3 holds, except that the consent page's language switcher href (BR-408) may echo that authorize request's own query, `state` included, HTML-escaped, back to the browser that sent it; no other response gains a request value, and error pages still carry none.

## Rationale

Codes, tokens, cookies and secrets in errors or logs would leak credentials to clients and operators. Source: [F-010 v1](../features/F-010-oauth-proxy.md), AC-26.

## Examples

v5 examples:

- **Given** 1,000 live consents, flows or codes
  **When** a valid request needs another entry
  **Then** it refuses with exactly one `store_full` containing only the store
  name and `count:1000`, without a handler event. Maps to
  `BR-143 v5 AC-09 each full-store refusal emits one event`.
- **Given** 1,000 clients or families
  **When** an existing eviction path admits an entry
  **Then** eviction continues with exactly one `store_full` containing only
  that store and `count:1000`. Maps to the same AC-09 test.
- **Given** expired entries have been purged below capacity
  **When** a valid request needs another entry
  **Then** admission succeeds without a capacity event. Maps to the same AC-09 test.

Historical examples (previous versions):

- **Given** a full flow with recognizable synthetic secrets
  **When** every refusal path runs with a capturing logger
  **Then** no refusal or log entry contains any secret.
- **Given** an upstream `error_description`
  **When** the client redirect is built
  **Then** it is not forwarded.
- **Given** every CIMD refusal path
  **When** the logger and stderr are captured
  **Then** only the BR-394 events and the `reason` field are added, and no CIMD URL, host, address, document member or TLS text appears (v3)
- **Given** an authorize request with `state` `"<x>'&` (v4)
  **When** the consent page and every error page are rendered
  **Then** `%22%3Cx%3E%27%26` appears once, inside the consent page's switcher href, and in no error page; the raw and plain HTML-escaped forms appear nowhere
