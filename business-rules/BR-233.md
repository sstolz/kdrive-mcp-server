## Rule

`ops/runner/install.sh` is the single owner-run entry point, run as root (directly or through `sudo`). Before any change it refuses, exiting nonzero with a fixed message per case, when the machine is not `x86_64`, `/dev/kvm` is missing, `nft` is missing, it is not root, or the arguments are not exactly one of: `--token-file <path>`, `--check`, `--uninstall`. Install mode reads the token only from the file at `<path>` (a regular non-symlink file, else a fixed refusal), never from an argument value, the environment or a prompt; it runs `host-setup.sh` (BR-220), installs the pinned Lima release after checking its SHA-256, writes the token to the BR-223 file as `kdrive-runner` from stdin (`runuser -u kdrive-runner`, `umask 077`, no-follow: a symlink at that path is a fixed refusal), so root never opens a path inside that user's home; a re-run with a token whose SHA-256 differs from the stored one replaces it (rotation) and prints a fixed "token rotated" line, enables and starts `kdrive-runner-nft.service` (the egress table is loaded before any VM exists), then runs `supervise.sh golden` (BR-224) and the remaining steps as `kdrive-runner`, then enables and starts `kdrive-ci-runner.service`. Each step first checks its target state and skips when it already holds, so a second run changes nothing and prints a fixed "already installed, no change" line. `--check` changes nothing and exits nonzero when the user, groups, loaded rules, Lima version, golden overlay, token file mode and owner, or unit state differ from the installed state. `--uninstall` first stops and disables `kdrive-ci-runner.service`, then removes only what install mode created (that unit, the `kdrive-runner-nft.service` unit and its `inet kdrive_runner` table, the Lima instance and golden overlay, and the generated files of `/etc/kdrive-runner/` except the owner's `extra-internal.conf`); it keeps the user, its home, the token file, the `<path>` file and every other service, and prints a fixed reminder to revoke the token. Its output never contains the token, a JIT configuration, a host name or an address.

## Rationale

One idempotent, refusing-by-default installer keeps the owner's server changes reviewable and reversible, and never handles the token outside a file (D-16). Source: [F-015 v1](../features/F-015-self-hosted-runner.md).

## Examples

- **Given** stubbed tools on an `aarch64` machine
  **When** `install.sh --check` runs
  **Then** it exits nonzero with its fixed message and records no changing call
- **Given** an installed stubbed state
  **When** `install.sh --token-file <path>` runs again
  **Then** it records no changing call and prints `kdrive-runner install: already installed, no change`
