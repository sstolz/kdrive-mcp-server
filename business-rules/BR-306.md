# BR-306 — CIMD fetch

## Rule

**v3 (F-052 v1, #72, accepted; the active rule).** A complete header block accepted by Node's HTTP parser with status 101, within the existing 8,192-byte bound, ends the CIMD fetch immediately as `{ok:false, reason:"status", status:101, transient:false}`, destroying the request, dedicated agent and any upgraded socket, clearing its deadline and releasing its BR-309 fetch slot without awaiting body bytes, peer closure or the 5,000 ms deadline. A status-line match by the byte watcher alone does not establish status 101: parser errors retain the existing `connection` / `transient:true` classification and status 0 when no response was accepted. Header overflow still takes precedence as `size`, status 0, `transient:false`.

The previous version otherwise holds. Its accepted text is preserved below
as history; v3 is the active rule.

The proxy fetches an acceptable CIMD client ID with one HTTPS `GET` to that exact URL whose only request headers are `Host`, `Accept: application/json`, `User-Agent: kdrive-mcp-server` (fixed, no version or host detail) and `Connection: close`: no `Accept-Encoding`, no cookie, no `Authorization` header and no other credential. It verifies the certificate for the URL host against Node's default CA store (the bundled roots plus any `NODE_EXTRA_CA_CERTS`), on the URL port (443 when absent). The request uses a dedicated `https.Agent` created without `proxyEnv`, so `NODE_USE_ENV_PROXY`, `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY` have no effect on it, with keep-alive off and `rejectUnauthorized: true` set explicitly, so `NODE_TLS_REJECT_UNAUTHORIZED=0` cannot disable verification (as for the kDrive transport, BR-191 and BR-216 v2). The host is resolved exactly once, never through `dns.lookup` (getaddrinfo on the libuv threadpool), but through a `dns.promises.Resolver` (c-ares, outside the threadpool) created for this fetch with `timeout` 2,000 ms and `tries` 2, which queries `resolve4` and `resolve6` in parallel; the answer is the union of both. A query that ends with `ENODATA` or `ENOTFOUND` contributes no address; any other query error fails the fetch as `resolution`. When the 5,000 ms deadline passes the proxy calls the resolver's `cancel()`, so no query outlives the fetch. Every returned address is checked under BR-307, and if any is blocked, or the union is empty, the fetch fails without connecting. Otherwise the agent's `lookup` returns, from memory, every checked address and only those (the `all` form, `resolve4` answers first, then `resolve6` answers, each in answer order), and the connection is made with `autoSelectFamily` true, so Node's connection attempts fall over from one checked address to the next until one connects or the 5,000 ms deadline passes; no second resolution happens for this fetch. The fetch succeeds only with status 200 (no redirect is followed; every other status fails), a `Content-Type` media type `application/json` or `application/<name>+json` (parameters ignored, case-insensitive), no `Content-Encoding` other than `identity` (the body is never decompressed; any other coding is a terminal `content_type` failure), a body of at most 5,120 bytes (reading stops and fails at the 5,121st byte, whatever `Content-Length` says) and completion within 5,000 ms from the start of the resolution. A failure is transient when the resolution fails, the connection or TLS handshake does not complete for a reason other than a certificate verification failure, the 5,000 ms elapse, or the status is 429 or 5xx; every other failure is terminal.

**v2 (F-033 v1, #26; accepted on main `6ef8b55`; superseded by v3)** — v1 holds, except that every header block of the response has at most 8,192 bytes. The first block starts at the first received byte of the response, and each later block at the byte after the `\r\n\r\n` that ends an interim `1xx` block. A block's status line starts at its first byte that is neither CR nor LF, and the block ends with the first `\r\n\r\n` at or after that byte, inclusive. Every byte from the start of a block is counted, the CR and LF bytes before its status line and the whitespace in its header lines included; CR and LF bytes before a status line never end a block. Each interim `1xx` block and the final (non-`1xx`) block are bounded separately. The header bound is checked on each received chunk before Node's HTTP parser receives that chunk (the header watcher's `data` listener is added with `socket.prependListener`, since Node's client attaches its parser listener before it emits `socket`), and therefore before the status, `Content-Type` and `Content-Encoding` checks. As soon as more than 8,192 bytes of one block have been received and none of its first 8,192 completes it, the fetch fails as `size`, terminal, with `status` 0 (BR-394 v2), whatever status line the block starts with, and no further header byte is buffered. Only the header bound runs before the parser: the v1 body count starts after the final block and keeps its v1 order, after the status, `Content-Type` and `Content-Encoding` checks, so a response whose final block passes the header bound fails as `status` or `content_type` when those checks refuse it, whatever its body length and however its bytes are split, and otherwise still fails as `size` at the 5,121st body byte, after any interim block. The request sets Node's `maxHeaderSize` to 16,384 bytes, so Node's own limit stays above the bound whatever `--max-http-header-size` says.

## Rationale

The fetch is an SSRF primitive and must not be steerable by DNS, proxies, redirects, compression or slow peers, nor exhaust the libuv threadpool (D-8). Source: [F-028 v2](../features/F-028-client-id-metadata-documents.md).

## Examples

v3 examples:

- **Given** a complete parser-accepted 101 header block of 8,192 bytes
  **When** the peer keeps its socket open
  **Then** the fetch immediately returns terminal `status` 101 and destroys the
  socket, without waiting for its deadline. Maps to
  `BR-306 v3 AC-10 101 settles before deadline and preserves header precedence`.
- **Given** an 8,193-byte header block beginning with status 101
  **When** the byte watcher receives the extra byte
  **Then** the fetch returns terminal `size`, status 0. Maps to the same AC-10 test.
- **Given** a bounded block whose status line matches 101 but whose headers the parser rejects
  **When** the fetch settles
  **Then** it returns transient `connection`, status 0. Maps to the same AC-10 test.
- **Given** three held fetches and a fourth receiving 101
  **When** the fourth settles
  **Then** a fifth URL can fetch while the three remain held; stale 101 entries
  are deleted. Maps to `BR-306 v3 BR-394 v3 AC-11 101 releases capacity and refuses terminally`.

Historical examples (previous versions):

- **Given** a server answering 302, 404, `text/html` or `Content-Encoding: gzip`
  **When** the production port fetches the URL
  **Then** a terminal failure (`status` or `content_type`) without following any redirect
- **Given** a body of 5,121 bytes, also with `Content-Length: 100`
  **When** the production port reads it
  **Then** a terminal `size` failure; 5,120 bytes are accepted
- **Given** a child with `NODE_USE_ENV_PROXY=1`, `HTTPS_PROXY` and `NODE_TLS_REJECT_UNAUTHORIZED=0`
  **When** the port fetches a trusted and an untrusted server
  **Then** the trusted fetch succeeds, the untrusted one fails as `certificate` and the proxy receives no connection
- **Given** a 200 JSON response with a header block of 8,192 bytes, then one of 8,193 bytes (v2)
  **When** the production port fetches it
  **Then** the first succeeds and the second fails as `size`, terminal, status 0
- **Given** a 503 response, or an interim `1xx` block followed by a 200 response, whose header block has 8,193 bytes (v2)
  **When** the production port fetches it
  **Then** it fails as `size`, terminal, status 0
- **Given** `\r\n\r\n` followed by a 200 JSON block, 8,193 bytes in total, or 8,193 CR/LF bytes and then a stall (v2)
  **When** the production port fetches it
  **Then** it fails as `size`, terminal, status 0
- **Given** a 200 `text/html` response with a 6,000-byte body, in one write or in split writes (v2)
  **When** the production port fetches it
  **Then** it fails as `content_type`, terminal, status 200, not as `size`
