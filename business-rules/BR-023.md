# BR-023 — Bounded configuration values and exact allowlists

Source: [F-002 v1](../features/history/F-002-v1.md), BR-023, frozen
2026-11-01 21:18:28 UTC after fresh independent approval.

## Rule

v3 (F-028 v2, #3, pending acceptance; v2 stays the accepted rule until then): adds the bounds of BR-291.

Accept resource bounds, paths, deny patterns and allowlists only
under the tables and grammars below. Reject invalid values rather than clamp,
coerce, silently discard entries or use a permissive fallback. Preserve exact
subject IDs and root paths; lowercase DNS domains only. Compare invitation
domains by exact normalized domain, never suffix/wildcard/subdomain matching.

The source specification's inventory, bounds, grammars, auth matrix, credential
contract, error mapping and preflight port supply the normative details for
this statement; this record does not redefine those tables.

Version 2 (F-019 v1, #103; accepted on main `68209fe`, 2026-11-11): adds the bounds of BR-290.

## Rationale

Reject ambiguous or unbounded input and avoid wildcard/suffix invitation authorization.

## Examples

These are contract examples using synthetic inputs. Execution evidence is
linked in Verification. Unless a row says otherwise, **Given** drive `7`, token
`SYNTHETIC_TOKEN`, authenticated HTTP with public URL
`https://service.example/mcp`, delegate issuer `https://issuer.example` and
subject `subject`, **When** `loadConfiguration` validates the changed value,
**Then** it produces the row's result. All test names below are in
[tests/config.test.ts](../tests/config.test.ts). A value such as `x × 1024`
means exactly that many ASCII `x` characters; byte counts are UTF-8 counts.

Each numeric row expands to four distinct examples, all covered by that exact
`scalar bounds %s` test row: `0` → `INVALID_VALUE` for the named setting;
`1` → accepted as `1`; the maximum → accepted unchanged; maximum + 1 →
`INVALID_VALUE` for that setting.
