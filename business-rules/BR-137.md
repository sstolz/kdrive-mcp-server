## Rule

For `authorization_code`, once a request passes BR-136 its code is consumed on its first presentation whatever the outcome; a consumed code stays in the store, marked consumed, until its 60-second lifetime ends. The consumption is committed before the first `await` of the request, so two concurrent redemptions yield at most one success. The grant yields 400 `invalid_grant` when the code is absent or unknown, consumed, expired, bound to another client, when `redirect_uri` is absent or not byte-identical to the bound one, or when `code_verifier` is not 43–128 unreserved characters (RFC 7636) whose S256 value equals the bound challenge; a `resource` that is present and differs from the bound one yields 400 `invalid_target`. A second presentation of a code that already produced tokens also revokes the refresh family created from it. Success returns 200 with `access_token` (BR-138), `token_type` `Bearer`, `expires_in` `3600` and, when the client registered `refresh_token`, a `refresh_token` starting a new family (BR-139).

## Rationale

Exact code redemption with PKCE prevents interception and replay; reuse signals theft and revokes the derived family. Source: [F-010 v1](../features/F-010-oauth-proxy.md), AC-16, AC-18.

## Examples

- **Given** a code
  **When** it is redeemed with a wrong verifier
  **Then** 400 `invalid_grant` and a later correct redemption fails.
- **Given** a redeemed code
  **When** it is redeemed again
  **Then** 400 `invalid_grant` and the first refresh token is revoked.
