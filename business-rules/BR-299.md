# BR-299 — A failed write latches the store

## Rule

v2 (F-028 v1, #3, pending acceptance; v1 stays the accepted rule until then): a row to be written that breaks a row rule of the version its transaction writes (BR-311) is a failed write, instead of a row that breaks a version 1 rule; otherwise unchanged. The first CIMD family write is therefore not a failed write.

A failed write is any of: an SQLite or I/O error, including a full disk, the page limit of BR-303 and a write on a closed store (BR-304); a row to be written that breaks a version 1 row rule; an `UPDATE` or `DELETE` keyed by primary key on a row held in memory whose `changes` count is not 1. It rolls the transaction back, throws nothing to the caller and latches the store; the request whose write failed answers the 503 below and issues no token, code or client. From then until restart the in-memory state keeps every revocation already decided but takes no other change, and registration and every token request answer 503 `{"error":"temporarily_unavailable"}` with the BR-136 headers (registration: `Cache-Control: no-store`) without reading or consuming a code or refresh token; authorization, consent and `/oauth/callback` requests answer the 503 HTML error page of BR-142 v2 without calling the upstream and without consuming a pending flow. One `store_write_failed` event is logged at the latch, except for a write on a store already closed under BR-304, which latches without logging any event.

## Rationale

In-memory and on-disk views would diverge under new writes after a failed commit, so the proxy stops accepting changes until restart. Source: [F-019 v1](../features/F-019-persistent-oauth-state.md).

## Examples

- **Given** a refresh whose family commit fails
  **When** the token request is handled
  **Then** 503 `temporarily_unavailable`, no token issued, and one `store_write_failed` event
- **Given** a latched store
  **When** a token request arrives
  **Then** 503 without reading or consuming the refresh token
- **Given** a latched store
  **When** an authorization request arrives
  **Then** the 503 `busy` HTML page without calling the upstream
- **Given** a write on a closed store
  **When** it is attempted
  **Then** the store latches and no event is logged
- **Given** a family row whose client ID fails the CIMD client ID syntax and names no client row
  **When** it is written
  **Then** a failed write that latches the store; the first CIMD family write is not a failed write (v2)
