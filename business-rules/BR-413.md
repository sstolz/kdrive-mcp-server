# BR-413 — Object resolution

## Rule

An object is resolved only through the merged cross-reference table. A type 1 object is parsed at its offset as `<number> <generation> obj`, one value, an optional stream framed by its `/Length`, and `endobj`; its number and generation equal the entry's. A type 2 object is read from the object stream named by the entry, which is itself a type 1 object with `/Type /ObjStm`, a direct `/N` of 1–4,096 and a direct `/First`. The header of an object stream is parsed once per invocation: `/N` pairs of object number and offset, offsets strictly increasing from 0 and each below the decoded length minus `/First`. The pair at the entry's index names the same object number; the object is the one value between its offset and the next (or the end), has generation 0 and is not a stream; `/Extends` is ignored. An indirect `/Length` resolves to a nonnegative integer object; resolving it never requires framing the stream it measures and opens at most one object stream, whose own `/Length` is direct or a type 1 integer object; an indirect `/Length` that needs more than one object stream, or an object stream whose own `/Length` is neither (a type 2 object, one living inside that object stream itself included), refuses as `CONTENT_UNAVAILABLE`. A reference `n g R` names the entry of object `n` and requires its generation to be `g`: a type 1 entry with generation `g`, any `g` the entry and the object header agree on, or a type 2 entry when `g` is 0; a reference whose generation differs, and a reference to a free, absent or mismatched object, in a role the projection needs, refuses as `CONTENT_UNAVAILABLE`. The canonical document renumbers what it emits, with generation 0 (BR-415). At most 4,096 distinct objects are resolved per invocation (the F-009 indirect-object ceiling); an object resolved again is served from the cache and not counted again.

## Rationale

Object streams and indirect lengths are common (F-034 S06, S08). Locating an object stream only through a type 1 entry, parsing its header once with strictly increasing offsets and limiting length resolution to one object stream stops recursion, length chains and repeated parsing; counting distinct objects keeps the F-009 ceiling meaningful. Source: [F-034 v1](../features/F-034-pdf-extraction-profile.md).

## Examples

- **Given** all non-stream objects stored in one object stream
  **When** page 1 is read
  **Then** its text
- **Given** a type 2 entry naming an object stream that is itself a type 2 object
  **When** page 1 is read
  **Then** `CONTENT_UNAVAILABLE` before PDF.js
- **Given** a page tree that needs 4,096 distinct resolved objects
  **When** page 1 is read
  **Then** its text
- **Given** a page tree that needs 4,097 distinct resolved objects
  **When** page 1 is read
  **Then** `LIMIT_EXCEEDED` before PDF.js
- **Given** an object stream with `/N` 4,097
  **When** page 1 is read
  **Then** `LIMIT_EXCEEDED` before PDF.js
- **Given** a content stream referenced as `4 1 R` whose entry and object have generation 1
  **When** page 1 is read
  **Then** its text
- **Given** a reference `5 1 R` to a type 2 object
  **When** page 1 is read
  **Then** `CONTENT_UNAVAILABLE` before PDF.js
