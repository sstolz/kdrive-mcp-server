# BR-300 — No upstream token or secret in the file

## Rule

The proxy never stores, in memory or in the file, an upstream access, refresh or ID token after the callback returns. The file never holds a refresh-token secret, client secret, authorization code, PKCE verifier, `nonce`, `state`, cookie value, access token, upstream client secret or signing-key material: client secrets and refresh-token secrets are stored only as their SHA-256 (input encoding in Contract details). A family stores the upstream `sub`, and, only when `oauthAllowedEmails` is nonempty, `email` when the ID token's `email` claim is a string (otherwise `NULL`) and `email_verified`.

## Rationale

The state file must not become a store of reusable secrets; hashes of random 256-bit secrets cannot be inverted. Source: [F-019 v1](../features/F-019-persistent-oauth-state.md).

## Examples

- **Given** a full flow with a secret client and an email allowlist
  **When** the file is read
  **Then** it holds SHA-256 hashes only and no secret, code, token, nonce or key
- **Given** an ID token whose `email` claim is not a string
  **When** the callback completes
  **Then** the family stores `NULL` as `email` and the store does not latch
