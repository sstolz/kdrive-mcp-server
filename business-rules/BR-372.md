# BR-372 — npm read-back

## Rule

### v2 — accepted (active)

Accepted on main `6a508ab` (#89 comments `89-acceptance-1-claude` and `89-acceptance-2-owner`).

After BR-359 v2 validation, npm read-back keeps the v1
retry limit of 20 attempts, 15 seconds apart, until all npm conditions
hold. For beta, all v1/v2 read-back conditions remain unchanged.
No stable-default support is added to beta. For stable,
`versions[<version>]` exists and records the exact release version;
`time[<version>]` exists;
`dist-tags.latest` equals `<version>`; that exact version has
`dist.attestations`; and its tarball bytes pass BR-379 v1 against the
verified tarball SHA-256. Resolving `latest` therefore selects that same
version, provenance and tarball. The exact `0.0.0-placeholder.0` entry
remains present with a non-empty `deprecated` string. Stable read-back
does not require the `beta` tag to move. A missing condition fails after
the bounded retry loop. No registry mutation occurs during read-back.

### v1 — accepted (superseded by v2)

`release-verify` runs the BR-359 validation first (no request on failure), then reads the npm package document, retrying up to 20 times 15 seconds apart until every condition holds: `versions` has `<version>`; `dist-tags.beta` equals `<version>`; `dist-tags.latest` is present, differs from `<version>` and names a version whose `deprecated` is a non-empty string; `versions[<version>].dist.attestations` exists.

## Rationale

A release is complete only when the registry serves the version under `beta`, with provenance, and `latest` still on the placeholder. Source: [F-024 v2](../features/F-024-gated-publication.md).

## Examples

- **Given** a registry where the version appears on the third attempt with everything holding
  **When** `release-verify` runs
  **Then** it passes
- **Given** attestations missing
  **When** `release-verify` runs
  **Then** it fails after the attempts run out
