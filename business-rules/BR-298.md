# BR-298 — Durable commit before the response

## Rule

v2 (F-028 v1, #3, pending acceptance; v1 stays the accepted rule until then): each row the store writes passes, before its transaction commits, the row rules of the format version that transaction writes (BR-311: version 1 or 2, Contract details) instead of always the version 1 rules; otherwise unchanged.

The store uses `journal_mode=DELETE`, `synchronous=FULL`, `secure_delete=ON` and `journal_size_limit=0`. `<path>-journal` is part of the store: under `locking_mode=EXCLUSIVE` it stays on disk while the store is open, is truncated to 0 bytes at each commit, is removed by a clean close, and after a crash may remain empty or as a hot journal; it is then checked by BR-293 and the next open succeeds. Each row the store writes passes the version 1 row rules of Contract details before its transaction commits. Each request that changes persisted state commits its changes in one synchronous transaction before its response is built and before its first `await` after the change: the registration response (201) only after the client row is committed, a token response carrying a refresh token only after its family row holds that token's hash, every family revocation or deletion (BR-140 v2 steps (2) and (3), BR-137 code replay, BR-301 identity refusal) before its `invalid_grant` response, and a BR-142 v2 eviction in the transaction of the entry that caused it, before that request's response. A client's last use is written on registration and in the transaction of each successful token response; an authorization request updates it in memory only.

## Rationale

A token or registration answered before its row is durable would be lost, or a revocation undone, by a crash. Source: [F-019 v1](../features/F-019-persistent-oauth-state.md).

## Examples

- **Given** a registration request
  **When** the client row commit succeeds
  **Then** the 201 response is built only after the commit
- **Given** a refresh token issued
  **When** the family row is committed
  **Then** the response carries a token whose hash is already stored
- **Given** a store left by a killed process
  **When** the next open runs
  **Then** the journal passes BR-293 and the rows load
- **Given** a version 1 file
  **When** a transaction inserts a CIMD family
  **Then** its rows pass the version 2 row rules and it commits with `user_version` 2 (v2)
