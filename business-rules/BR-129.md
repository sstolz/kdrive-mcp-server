## Rule

v2 (F-028 v1, #3, pending acceptance; v1 stays the accepted rule until then): the consent page content of BR-393 for CIMD clients.

Every valid authorization request shows a consent page; no consent is remembered. The page states the client's `client_name` labelled as self-declared and unverified (or "unnamed client"), the `client_id`, the exact `redirect_uri` of the request and the protected resource (audience), with every value HTML-escaped. It holds one form posting to `<issuer>/oauth/consent` with a hidden one-use consent identifier (32 random bytes) and `decision` `approve` or `deny`. The pending request is stored under that identifier for 600 seconds, bound to the browser cookie of BR-130. Page and error-page responses carry `Cache-Control: no-store`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; base-uri 'none'`. The consent handler consumes the identifier on its first presentation whatever the outcome; an unknown, expired or consumed identifier, a missing or mismatched cookie, or a `decision` other than `approve`/`deny` yields a 400 HTML error page. `deny` produces a client redirect with `error=access_denied`; `approve` starts the upstream leg (BR-131).

## Rationale

A static upstream client plus open registration is the MCP confused-deputy case; explicit consent per authorization prevents silent approvals. Source: [F-010 v1](../features/F-010-oauth-proxy.md), AC-08, AC-09.

## Examples

- **Given** a client named `<script>alert(1)</script>`
  **When** a valid authorization request arrives
  **Then** a consent page with the escaped name, the unverified label and the security headers.
- **Given** a pending consent
  **When** `decision=deny` is posted with the bound cookie
  **Then** 302 with `error=access_denied`, `state` and `iss`.
- **Given** a CIMD client
  **When** the consent page is shown
  **Then** it carries the BR-393 content; a registered client's page is unchanged (v2)
