# BR-278 — Configured roots are protected

## Rule

**v1 (active until v2 acceptance)**

The policy core denies (`ACCESS_DENIED`) a `trash`, `rename` or `move` operation whose `(drive_id, target ID)` pair equals any configured root pair (root `1` included), so the gate returns `denied` with zero intent records and zero mutation requests; this replaces F-003's sentence "A non-root configured root can be renamed".

**v2 (F-041 v1, #47 lot E, pending acceptance; v1 stays the active rule until then)**

The v1 direct-root refusal remains. In `write` and `share` modes, the
policy also refuses `trash`, `rename` and `move` whose source is a live
folder that is a strict ancestor of any configured root in the same drive,
using BR-427 evidence. The admitted gate returns exactly
`{result:"denied",op:O,code:"ACCESS_DENIED",attempts:0}`, with zero intent
and outcome records and zero mutation requests, and attempts the existing
single `denied` audit record (BR-246). Unknown ancestry also refuses under
BR-427. The protected-source predicate does not apply to a move destination;
other destination/effect checks remain. Copy, upload, create and restore
contracts are unchanged. Overlapping roots remain valid configuration.

## Rationale

A configured root is the operator's boundary; moving or renaming it would silently change the scope. Source: [F-017 v1](../features/F-017-controlled-tree-mutations.md).

v2 closes the indirect configured-root mutation bypass (R-17-2) selected
by the owner in #47 lot E, without banning overlapping roots or adding
write permissions. Source: [F-041 v1](../features/F-041-configured-root-ancestors.md).

## Examples

- **Given** configured roots `101:1` and `101:40`
  **When** `kdrive_trash` targets 40
  **Then** the result is `denied` with no intent record
- **Given** a second configured drive 102 whose root holds an item with ID 40
  **When** that item is renamed
  **Then** the result is `succeeded`

v2 examples (pending; v1 examples above remain active):

- **Given** roots `101:1` and `101:40`, with 40 under `/A/B/R`
  **When** trash, rename or move targets parent B or grandparent A
  **Then** every call returns `denied` / `ACCESS_DENIED`, `attempts:0`,
  one attempted `denied` record, no intent/outcome and no mutation request.
  Maps to `TestBR278_v2_AC01_parent_and_grandparent_refused_in_write_and_share`.
- **Given** the same roots and an unrelated sibling S
  **When** trash, rename or move targets S
  **Then** the permitted synthetic operation succeeds with one attempt,
  one intent and one outcome; direct operations on roots 1 and 40 still
  refuse. Maps to `TestBR278_v2_AC02_direct_roots_still_refused_and_siblings_allowed`.
- **Given** unrelated S and ancestor A
  **When** S moves into A
  **Then** the permitted synthetic move succeeds; moving A itself refuses.
  Maps to `TestBR278_v2_AC03_move_destination_is_not_a_protected_source`.
- **Given** a protected ancestor and an admitted run whose denied append fails
  **When** the policy refuses
  **Then** one append is attempted, the refusal is unchanged and no mutation
  starts. Maps to `TestBR278_v2_AC04_failed_denied_append_keeps_access_denied`.
