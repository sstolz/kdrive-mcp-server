## Rule

**v1 (F-010 v1; superseded by v2)**

For `authorization_code`, once a request passes BR-136 its code is consumed on its first presentation whatever the outcome; a consumed code stays in the store, marked consumed, until its 60-second lifetime ends. The consumption is committed before the first `await` of the request, so two concurrent redemptions yield at most one success. The grant yields 400 `invalid_grant` when the code is absent or unknown, consumed, expired, bound to another client, when `redirect_uri` is absent or not byte-identical to the bound one, or when `code_verifier` is not 43–128 unreserved characters (RFC 7636) whose S256 value equals the bound challenge; a `resource` that is present and differs from the bound one yields 400 `invalid_target`. A second presentation of a code that already produced tokens also revokes the refresh family created from it. Success returns 200 with `access_token` (BR-138), `token_type` `Bearer`, `expires_in` `3600` and, when the client registered `refresh_token`, a `refresh_token` starting a new family (BR-139).

**v2 (F-035 v1, #46; accepted on main `703bece`)** — v1 holds, except for the order of the checks, redirect URI compatibility and what a refused request changes. After BR-136, a token request with `grant_type=authorization_code` is decided in this order: (1) `code` absent or unknown: 400 `invalid_grant`; (2) the code's 60-second lifetime has ended (now ≥ creation + 60 s): 400 `invalid_grant`; (3) the code is bound to another client, a present `redirect_uri` is not byte-identical to the authorization request's bound URI, an omitted `redirect_uri` fails the omission condition below, or `code_verifier` is not 43–128 unreserved characters whose S256 value equals the bound challenge: 400 `invalid_grant`; (4) `resource` is present and differs from the bound one: 400 `invalid_target`; (5) the code is consumed: its refresh family, when one was created from it and still exists, is revoked (deleted, committed before the response under BR-298 v2, one `refresh_family_revoked` event, BR-140 v2) and the answer is 400 `invalid_grant`; with no such family, 400 `invalid_grant` and nothing else; (6) otherwise the code is marked consumed and the request succeeds as under v1. Steps (1)–(4) change nothing but the client's in-memory last use (as under v1): the code stays as it was (unconsumed or consumed), no family is revoked, no row is written and no event is logged. Step (6) marks the code consumed in the same synchronous step that starts its family and commits, before the first `await` of the request, so of two concurrent requests that both pass (1)–(4) one succeeds and the other is a step (5) replay. A consumed code is kept until its lifetime ends, as under v1; from then on step (2) answers it, whether or not the purge has removed it, and no replay revokes. Omission of `redirect_uri` is accepted only when the authorization request's URI was byte-identical to the client's single registered redirect URI in the client snapshot at authorization (the resolved document snapshot for CIMD); multiple registered URIs or a loopback port differing from the registered URI require an explicit exact match to the bound URI. An empty value is present, not omitted.

## Rationale

Exact code redemption with PKCE prevents interception and replay; reuse signals theft and revokes the derived family. Source: [F-010 v1](../features/F-010-oauth-proxy.md), AC-16, AC-18.

## Examples

- **Given** a code
  **When** it is redeemed with a wrong verifier
  **Then** 400 `invalid_grant` and a later correct redemption fails.
- **Given** a redeemed code
  **When** it is redeemed again
  **Then** 400 `invalid_grant` and the first refresh token is revoked.
- **Given** a fresh code (v2)
  **When** it is presented with a wrong verifier
  **Then** 400 `invalid_grant`, nothing changes, and a later correct redemption gets 200
- **Given** a redeemed code (v2)
  **When** it is presented again with another client's credentials
  **Then** 400 `invalid_grant` and the family is not revoked
- **Given** a redeemed code (v2)
  **When** it is presented again with every binding matching, before its 60 s end
  **Then** 400 `invalid_grant` and its family is revoked

- **Given** a fresh code whose authorization URI equals its client's single registered URI (v2)
  **When** redemption omits `redirect_uri` and all other bindings match
  **Then** 200 with no mismatch event
- **Given** multiple registered URIs or an authorization loopback port differing from the single registered URI (v2)
  **When** redemption omits `redirect_uri`
  **Then** 400 `invalid_grant`, no event, and a later explicit match succeeds
- **Given** a fresh code and a present matching, mismatching or empty `redirect_uri` (v2)
  **When** redemption otherwise matches
  **Then** the exact match succeeds; mismatching and empty values fail without consumption or logging
