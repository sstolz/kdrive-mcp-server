## Rule

v3 (F-028 v2, #3, pending acceptance; v2 stays the accepted rule until then): the events and the `reason` field of BR-394.

The optional logger receives only a fixed event name from the list in Contract details and fields limited to: handler name, OAuth error code, HTTP status, store name and count. No handler response, error page, thrown error message or logger call contains a client secret, upstream secret, authorization code, PKCE verifier, `nonce`, upstream `state`, client `state`, cookie value, access, refresh or ID token, `client_id`, identity value or signing-key material, except the response that issues that value to its holder (registration response, consent page, code redirect, token response, upstream redirect `state`/`nonce`/challenge, `Set-Cookie`, and the client redirect's echoed `state`).

Version 2 (F-019 v1, #103; accepted on main `68209fe`, 2026-11-11): the event list adds BR-312's events and the field list adds `clients` and `families`.

## Rationale

Codes, tokens, cookies and secrets in errors or logs would leak credentials to clients and operators. Source: [F-010 v1](../features/F-010-oauth-proxy.md), AC-26.

## Examples

- **Given** a full flow with recognizable synthetic secrets
  **When** every refusal path runs with a capturing logger
  **Then** no refusal or log entry contains any secret.
- **Given** an upstream `error_description`
  **When** the client redirect is built
  **Then** it is not forwarded.
- **Given** every CIMD refusal path
  **When** the logger and stderr are captured
  **Then** only the BR-394 events and the `reason` field are added, and no CIMD URL, host, address, document member or TLS text appears (v3)
