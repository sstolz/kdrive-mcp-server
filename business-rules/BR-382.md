# BR-382 — A call waits at most 12,000 ms

## Rule

A call still waiting 12,000 ms of monotonic time after it joined leaves the queue and returns `SERVER_BUSY`, with zero kDrive requests and zero audit records; the calls behind it keep their relative order. When the slot is released at the instant the wait reaches 12,000 ms, whichever of the release and the wait timer runs first, the call is refused with `SERVER_BUSY` and the slot goes to the next waiter (BR-383).

## Rationale

12,000 ms exceeds the 10,000 ms invocation deadline, so a call directly behind one read always runs, while an admitted read still answers well within client request timeouts (F-026 D-2). Source: [F-026 v1](../features/F-026-bounded-invocation-queue.md).

## Examples

- **Given** a gate run holding the slot that settles 11,999 ms after a read joined
  **When** the slot is released
  **Then** the read takes the slot and succeeds
- **Given** a gate run that settles 12,001 ms after a read joined
  **When** 12,000 ms have passed
  **Then** the read returns `SERVER_BUSY` with zero requests and a call behind it keeps its place
- **Given** a gate run that settles exactly 12,000 ms after a read joined, and a second read behind it
  **When** the release and the read's wait timer fall due at the same instant (either callback first)
  **Then** the first read returns `SERVER_BUSY` with zero requests and the second read takes the slot
- **Given** two stdio waiters that joined in the same tick behind a gate run lasting 20,000 ms
  **When** 12,000 ms have passed
  **Then** both get `SERVER_BUSY` and the stdio session stays open (with BR-388)
