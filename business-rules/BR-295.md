# BR-295 — Version 1 SQLite format and ordered open checks

## Rule

v2 (F-028 v2, #3, pending acceptance; v1 stays the accepted rule until then): step (5) refuses a `user_version` above 2 with `OAUTH_STATE_VERSION`; step (9) applies the row rules of the file's own version (a CIMD family in a version 1 file is `OAUTH_STATE_CORRUPT`); step (11) sets the version under BR-311. Version 1 to 2 needs no migration step: the schema is identical.

The file is an SQLite database with `application_id` `0x4B444F53` and `user_version` `1`, holding exactly the version 1 schema of Contract details, and is opened and checked in this order, the first failing step deciding the code: (1) the BR-293 checks (`OAUTH_STATE_UNAVAILABLE`); (2) a file larger than 67,108,864 bytes by the step (1) `lstat` gives `OAUTH_STATE_CORRUPT`; a nonempty file is refused with `OAUTH_STATE_CORRUPT` unless its first 100 bytes, read through a descriptor opened with `O_RDONLY | O_NOFOLLOW | O_CLOEXEC` and closed before SQLite opens the path, exist, start with the 16 bytes `SQLite format 3\0` and have bytes 18 and 19 both equal to 1 (rollback journal, not WAL); (3a) SQLite opens the path, then the second BR-293 `lstat` identity check runs (`OAUTH_STATE_UNAVAILABLE`); (3b) the BR-294 `BEGIN EXCLUSIVE` runs, its failure mapped by the primary result code `errcode & 0xff` of the thrown error (extended codes such as `SQLITE_BUSY_RECOVERY` 261 map with their primary code): `SQLITE_BUSY` (5) or `SQLITE_LOCKED` (6) gives `OAUTH_STATE_LOCKED`, `SQLITE_CORRUPT` (11) or `SQLITE_NOTADB` (26) gives `OAUTH_STATE_CORRUPT`, any other code gives `OAUTH_STATE_UNAVAILABLE`; `trusted_schema=OFF` and `secure_delete=ON` are set before the schema or any row is read; `PRAGMA journal_mode` must then return `delete`, otherwise `OAUTH_STATE_CORRUPT`; a zero-length file is then initialized to version 1, meta included, in one transaction; (4) an `application_id` other than `0x4B444F53` gives `OAUTH_STATE_CORRUPT`; (5) a `user_version` above 1 gives `OAUTH_STATE_VERSION`, before any other check of the content, and a `user_version` below 1 gives `OAUTH_STATE_CORRUPT`; (6) a `PRAGMA integrity_check` result other than the single row `ok` gives `OAUTH_STATE_CORRUPT`; (7) a schema other than the version 1 schema gives `OAUTH_STATE_CORRUPT`: its `sqlite_schema` rows, compared on `type`, `name`, `tbl_name` and `sql`, differ in any way from the rows that the version 1 initialization creates, so any extra table, index, trigger or view is refused; (8) more rows than BR-303 allows in `clients` or `families`, counted with `COUNT(*)` before any row is read and before the purge, gives `OAUTH_STATE_CORRUPT`; (9) a row of any table, expired or not, that breaks a version 1 row rule of Contract details gives `OAUTH_STATE_CORRUPT`; (10) the meta check of BR-296 (`OAUTH_STATE_MISMATCH`); (11) one transaction, always committed, that sets `user_version` to 1 again (a real write even when nothing is purged) and runs the BR-302 startup purge. An SQLite error thrown by steps (4) to (10) gives `OAUTH_STATE_CORRUPT` when its `errcode & 0xff` is `SQLITE_CORRUPT` (11) or `SQLITE_NOTADB` (26), and `OAUTH_STATE_UNAVAILABLE` otherwise. A later format version migrates upward only, from each older version in one exclusive transaction after step (5), and is defined by the feature that introduces it, including where its checks run; version 1 has no migration. An SQLite or I/O error in the zero-length initialization, a migration or the step (11) transaction (a read-only open included) rolls that transaction back and stops startup with `OAUTH_STATE_UNAVAILABLE`. A refusal after SQLite opened the path closes that connection, releasing its lock, before the error is raised. A refused file is left unchanged, with one exception: SQLite's rollback of a hot journal that passed BR-293, which happens when SQLite opens the file, is the only change allowed before a refusal under this rule or BR-296.

## Rationale

A file is trusted only when it is exactly the schema the proxy wrote, so every other shape is refused with a code the operator can act on. Source: [F-019 v1](../features/F-019-persistent-oauth-state.md).

## Examples

- **Given** a zero-length file
  **When** the store opens
  **Then** it is initialized to version 1 with the meta values
- **Given** `user_version` 2 on a version 1 schema
  **When** the store opens
  **Then** `OAUTH_STATE_VERSION`
- **Given** a file that is not an SQLite database
  **When** the store opens
  **Then** `OAUTH_STATE_CORRUPT`
- **Given** a table with 1,001 families
  **When** the store opens
  **Then** `OAUTH_STATE_CORRUPT`
- **Given** a stored family whose `created` is after `token_issued`
  **When** the store opens
  **Then** `OAUTH_STATE_CORRUPT`
- **Given** a file with `user_version` 3
  **When** the store opens
  **Then** `OAUTH_STATE_VERSION` (v2)
- **Given** a version 1 file holding a CIMD family row
  **When** the store opens
  **Then** `OAUTH_STATE_CORRUPT` (v2)
