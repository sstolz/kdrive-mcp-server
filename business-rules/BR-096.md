## Rule

**v2 (F-052 v1, #72; pending acceptance).** Token-step admission additionally requires no endpoint disagreement between the two usable discovery documents: for each of `authorization_endpoint` and `token_endpoint`, two present values (neither `undefined`, including `null` and non-strings) disagree exactly when their `JSON.stringify` results differ, matching the existing discovery anomaly without URL normalization. Admission checks run in this order: discovery usable, PKCE S256 yes, endpoint disagreement, effective-endpoint HTTPS, then the supported client-secret authentication-method check. Disagreement refuses before either interactive prompt, authorization URL output or token exchange and writes an `unsupported` report with the existing `<member> differs between documents` anomalies and the exact `tokenStep` `refused: <members> differs between documents`, where `<members>` is `authorization_endpoint`, `token_endpoint`, or `authorization_endpoint, token_endpoint` in that order.

The previous version otherwise holds. Its accepted text is preserved below;
acceptance of that text does not establish acceptance of v2.

The `token` step sends a request only when discovery is usable, effective PKCE S256 is `yes`, both endpoints are `https` URLs, `--resource` is a canonical audience and `--redirect-uri` is an `http` loopback URI without userinfo on `127.0.0.1`, `[::1]` or `localhost` with an explicit port other than 80; a provider-condition refusal writes an `unsupported` report and an owner-input refusal writes none and exits nonzero. The request uses response type `code`, a fresh 43-character S256 PKCE verifier, fresh 32-byte `state` and `nonce`, scope `openid` plus extra scopes and the `resource`.

## Rationale

The owner's browser and tokens are engaged only for a provider that can safely complete the flow, and only with a redirect that stays on the owner's machine. Source: [F-008 v1](../features/F-008-oidc-qualification.md), AC-05, AC-06.

## Examples

v2 examples:

- **Given** two usable documents with different `authorization_endpoint` values
  **When** token admission runs after usable discovery and PKCE S256 `yes`
  **Then** it writes an `unsupported` report with
  `refused: authorization_endpoint differs between documents`, without a prompt
  or token request. Maps to `BR-096 v2 AC-01 endpoint disagreement refuses token`.
- **Given** identical endpoints, or an endpoint absent from one usable document
  **When** token admission runs
  **Then** the existing first-defined endpoint and HTTPS checks apply.
  Maps to `BR-096 v2 AC-02 endpoint agreement and discovery boundaries`.

Historical examples (previous versions):

- **Given** redirect URI `http://127.0.0.1:80/cb`.
  **When** `token` starts.
  **Then** it exits nonzero with no request and no report.
- **Given** redirect URI `http://127.0.0.1:8080/cb` and a qualifying provider.
  **When** `token` starts.
  **Then** the authorization URL is printed.
- **Given** effective PKCE S256 `unknown`.
  **When** `token` starts.
  **Then** no authorization or token request is made and an `unsupported` report is written.
