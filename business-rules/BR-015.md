# BR-015 — Mandatory CI with separately enabled official-scanner analysis

## Rule

v7 (F-023 v1, #1, pending acceptance; v6 below stays the accepted rule until then): v6 holds with these changes. The exact job set adds `privacy-scan` (BR-341). Every job runs on `ubuntu-24.04` (BR-225 v3). The Make-only `run` allowlist adds `make privacy-scan`, admitted only in `privacy-scan`; `make setup` is not admitted there. The non-Make `run` texts add `PRIVACY_FORK_NOTICE`, admitted only in `privacy-scan` (eleven occurrences). The word `secrets` (v3 matching) appears only inside the `env` values of the two Sonar analysis steps and of the `privacy-scan` step 3; each such value matches `^\$\{\{ secrets\.[A-Z_]+ \}\}$`. The Sonar gate set stays the five build gates. (v6: `secrets` only in the two analysis steps.)

v6 (F-020 v1, #104; accepted on main `b6acf86`, 2026-11-11): v5 holds with these changes. The exact job set adds `audit` (BR-320). The Make-only `run` allowlist adds `make audit`, admitted only in the `audit` job. The admitted non-Make `run` texts are unchanged (ten occurrences). The gates that Sonar waits for (`sonar` and `sonar-pr` `needs`, the two-run gate check) stay the five build gates `lint`, `format`, `typecheck`, `test` and `build`.

v5 (F-015 v1, pending acceptance; v4 below stays the accepted rule until then): v4 holds with these changes. The exact job set adds `changes`, `fork-refusal` and `ci-result`. Every job except `fork-refusal` runs on the BR-225 label array `[self-hosted, linux, x64, kdrive-ci]`, and every job has the BR-225 `timeout-minutes`. `lint`, `format`, `typecheck`, `test` and `build` each have `needs: [changes]` and the job `if` exactly `needs.changes.outputs.heavy != 'false'` (BR-227), so they run on every `push` and `workflow_dispatch` and on every same-repository PR except a records-only one (BR-226); the workflow still has no `paths`, `paths-ignore`, `branches-ignore` or `tags` filter. The Make-only `run` allowlist adds `make ci-changes`, admitted only in the `changes` job. The non-Make `run` texts add the `ci-result` failure text (BR-227), a named constant in `tests/helpers/ci-policy.ts` admitted only in `ci-result`, and admit the BR-149 fork-refusal text also in the `fork-refusal` job (ten occurrences in all). The workflow has the BR-228 top-level `concurrency`.

v4 (F-013 v1, pending acceptance; v3 below stays the accepted rule until then): v3 holds with these changes. The exact job set adds `image`, with the BR-183 shape: `ubuntu-24.04`, `permissions: contents: read`, `timeout-minutes: 30`, no `if`, `needs`, `env` or secrets reference, `strategy` `fail-fast: false` with `matrix.platform` exactly `[linux/amd64, linux/arm64]`, and the steps pinned checkout, `make image-binfmt`, `make image`, `make image-smoke`, each with step `env` exactly `IMAGE_PLATFORMS: ${{ matrix.platform }}`. The Make-only `run` allowlist adds `make image-binfmt`, `make image` and `make image-smoke`, admitted only in the `image` job. `uses` still admits only `actions/checkout@<40-hex SHA>`.

v3 (F-011 v2, accepted on main `bc09d56`): v2 holds with these changes. Five non-Make `run` texts are admitted (adding the BR-151 final Git-metadata step; eight occurrences), and the final step is the last step of both Sonar jobs with the condition exactly `always()`. The word `secrets`, matched case-insensitively as a whole word over every parsed key and string value of the workflow, appears only inside the `env` values of the two analysis steps; any other place or form (a `with`, `run` or `if` value, another job, a `secrets` key, bracket syntax, `toJSON(secrets)`, upper-case `SECRETS.`) is rejected.

v2 (F-011, accepted on main `bc09d56`; v1 below is kept for history):

BR-015 v1 holds (every main PR/push runs the five mandatory Docker/Make jobs;
read-only permissions; pinned Actions; no path filters, publication, release or
tag path; trusted-main `sonar` job after all gates, serialized, only when
enabled), with these changes: the `sonar` job's analysis step receives exactly
`SONAR_ENABLED`, `SONAR_HOST_URL` from `secrets.SONAR_HOST_URL`, `SONAR_TOKEN`
from `secrets.SONAR_TOKEN` and `SONAR_PRISTINE_TAR`
(`${{ runner.temp }}/pristine.tar`); no other job references
`secrets.SONAR_TOKEN`; the `sonar` job never references `secrets.SONAR_PR_TOKEN`;
the `sonar` job runs the BR-151 pristine-export step before `make setup` and the
BR-151 comparison step between `make setup` and its analysis step; no CI step
sets `SONAR_TOKEN_FILE` or `SONAR_HOST_URL_FILE`; and the PR analysis is the
separate `sonar-pr` job of BR-149. The v1 "Make-only `run`" rule admits exactly
four non-Make `run` texts — the BR-151 pristine export, the BR-151 comparison,
the BR-149 fork refusal and the BR-149 disabled notice — each a named constant
in `tests/helpers/ci-policy.ts`, and each non-Make step occurrence equals one of
them. (v1: no host secret; any PR analysis rejected.)

v1 (accepted):

retain every-main-PR/push mandatory lint/format/typecheck/test/build
jobs, Docker Make setup/gates, read-only permissions, pinned Actions, no path
filters or publication/release/tag paths. Conditional Sonar follows successful
gates only on separately enabled trusted-main push/manual events, serialized per
project; PR/forks never receive a token/upload. Use runtime SONAR_TOKEN without
legacy compatibility/version/evidence environment prerequisites. Missing token,
failed scanner/Quality Gate, network error or timeout fails enabled analysis.
Local file provisioning does not transfer secrets to GitHub or enable CI Sonar.

## Rationale

preserve required CI gates and credential isolation while aligning
optional analysis with the official scanner's supported project-token flow.
