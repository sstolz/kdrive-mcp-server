# BR-394 — CIMD events

## Rule

**v3 (F-052 v1, #72, accepted; the active rule).** A CIMD authorization refused because of that 101 emits exactly one `client_metadata_refused` with `{handler:"authorize", reason:"status", status:101}`. For full-consent-store authorization refusals, BR-143 v5 supersedes the F-028 Contract details row and BR-394 v1–v2 handler requirement: the whole log delta is exactly one store_full with only store and count.

The previous version otherwise holds. Its accepted text is preserved below
as history; v3 is the active rule.

The proxy adds the event `client_metadata_refused` (handler `authorize`, fields `reason` and `status`), with `reason` one of `not_allowed` (BR-305), `blocked_address`, `resolution`, `connection`, `certificate`, `timeout`, `status`, `content_type`, `size`, `document` (BR-306–BR-308, and a `redirect_uri` not kept from the document) or `busy` (BR-309). Every refused authorization request logs exactly one event, the one Contract details "Authorization refusal events" assigns to it: with an empty list, and for a `client_id` that does not start with `https://`, today's event only; `client_metadata_refused` only with a nonempty list. The proxy also adds the event `client_metadata_fetched` (fields `status` and `count`, where `count` is the number of cache entries) logged once per completed successful fetch. In both events `status` is the HTTP status code of the document response, or `0` when no response status was received (`not_allowed`, `blocked_address`, `resolution`, `connection`, `certificate`, `busy`, and `timeout` before the status line); it is therefore always 200 in `client_metadata_fetched`. The status of the proxy's own page follows from `reason` (BR-309). `reason` joins the BR-143 field list. No event, response, page other than the consent page, or thrown message contains a CIMD URL, host, resolved address, document member or TLS error text.

**v2 (F-033 v1, #26; accepted on main `6ef8b55`; superseded by v3)** — v1 holds, except that the reasons with `status` 0 also include `size` from the BR-306 v2 header bound: it is decided before any status line is parsed, even when the oversized block starts with one (a 503 or a 302 included). A `size` from the body bound keeps the received status (200). A terminal `size` deletes a stale entry and gives the 400 page under BR-309.

## Rationale

Operators need one event per refusal with a reason they can act on, while logs must not carry client URLs, hosts, addresses or TLS text. Source: [F-028 v2](../features/F-028-client-id-metadata-documents.md).

## Examples

v3 examples:

- **Given** a CIMD fetch refused on parser-accepted status 101
  **When** authorization is refused
  **Then** exactly one `client_metadata_refused` contains
  `{handler:"authorize", reason:"status", status:101}` and the terminal page
  returns 400. Maps to
  `BR-306 v3 BR-394 v3 AC-11 101 releases capacity and refuses terminally`.
- **Given** a full consent store
  **When** authorization needs another consent
  **Then** its only event is `store_full` with `{store:"consents", count:1000}`,
  without `handler`, under BR-143 v5. Maps to
  `BR-143 v5 AC-09 each full-store refusal emits one event`.

Historical examples (previous versions):

- **Given** a nonempty list and a CIMD client ID under an unlisted origin
  **When** authorize refuses it
  **Then** exactly one `client_metadata_refused` with `reason` `not_allowed` and `status` 0
- **Given** an empty list and an https client ID
  **When** authorize refuses it
  **Then** exactly one `authorization_refused` and no `client_metadata_refused`
- **Given** a successful fetch
  **When** the document is cached
  **Then** one `client_metadata_fetched` with `status` 200 and the cache count
- **Given** a response whose 503 status line starts an 8,193-byte header block (v2)
  **When** the fetch fails on the header bound
  **Then** one `client_metadata_refused` with `reason` `size` and `status` 0
