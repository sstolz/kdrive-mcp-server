## Rule

The `token` step sends a request only when discovery is usable, effective PKCE S256 is `yes`, both endpoints are `https` URLs, `--resource` is a canonical audience and `--redirect-uri` is an `http` loopback URI without userinfo on `127.0.0.1`, `[::1]` or `localhost` with an explicit port other than 80; a provider-condition refusal writes an `unsupported` report and an owner-input refusal writes none and exits nonzero. The request uses response type `code`, a fresh 43-character S256 PKCE verifier, fresh 32-byte `state` and `nonce`, scope `openid` plus extra scopes and the `resource`.

## Rationale

The owner's browser and tokens are engaged only for a provider that can safely complete the flow, and only with a redirect that stays on the owner's machine. Source: [F-008 v1](../features/F-008-oidc-qualification.md), AC-05, AC-06.

## Examples

- **Given** redirect URI `http://127.0.0.1:80/cb`.
  **When** `token` starts.
  **Then** it exits nonzero with no request and no report.
- **Given** redirect URI `http://127.0.0.1:8080/cb` and a qualifying provider.
  **When** `token` starts.
  **Then** the authorization URL is printed.
- **Given** effective PKCE S256 `unknown`.
  **When** `token` starts.
  **Then** no authorization or token request is made and an `unsupported` report is written.
