# BR-405 — The `lang` query parameter

## Rule

The `lang` query parameter is valid when the query holds it exactly once (`URLSearchParams.getAll("lang")` has one element) and that decoded value is identical to `en` or `fr` (lower case; `lang=%66r` is valid). Any other value (`FR`, `fr-CH`, `de`, empty) is ignored: the page language falls to BR-404 (2), and nothing is refused for it. For the OAuth checks `lang` is an unknown parameter of BR-128 v3: it never changes which check passes or fails, which event is logged, or which redirect or `error` is produced; like any parameter, a repeated `lang` on authorize or callback is the existing repeated-parameter refusal (400 page). `lang` is never copied into a client redirect (deny, refusal redirects, the code redirect), into the upstream authorization URL, into a pending consent, flow, code or the state file.

## Rationale

A cosmetic parameter must not break or change an authorization (F-031 D-4). Source: [F-031 v1](../features/F-031-oauth-proxy-page-languages.md).

## Examples

- **Given** a valid registered-client authorize request with `lang=FR`
  **When** authorize answers
  **Then** the English consent page (no `Accept-Language`)
- **Given** the same request with `lang=fr&lang=en`
  **When** authorize answers
  **Then** the 400 repeated-parameter page and the same `authorization_refused` event as a repeated `client_id`
- **Given** a deny posted from a French page
  **When** the consent handler answers
  **Then** a client redirect byte-identical to the one without `lang`, with no `lang`
