## Rule

The upstream ID token is accepted only when it is a compact JWS without `crit`, whose `alg` is in the F-008 BR-098 list, whose signature verifies against a usable key (BR-107) of the upstream JWKS whose `kid` equals the token's `kid` when both carry one, whose `alg` equals the token's `alg` when the key carries one, and whose key type and curve match the `alg` (RSA for `RS*`/`PS*`, P-256 for `ES256`, P-384 for `ES384`, `OKP` Ed25519 for `EdDSA`/`Ed25519`); whose `iss` equals the upstream issuer exactly; whose `aud` equals the upstream client ID or is an array containing it; whose `azp`, when present (and necessarily when `aud` is an array of more than one member), equals the upstream client ID; whose `nonce` equals the flow's nonce; whose `exp` is a number later than now; whose `iat` is a number; whose `nbf`, when present, is not later than now; and whose `sub` is a nonempty string of at most 255 bytes. No clock tolerance is applied. The JWKS is cached for at most 3,600 seconds; when the token carries a `kid` that no cached usable key matches, it is refetched at most once per 60 seconds; a token without `kid` triggers no refetch. A rejected ID token produces a client redirect with `error=server_error`. The upstream access token, refresh token and ID token are discarded after this check and never stored, returned or logged.

**v2 (F-035 v1, #46, pending acceptance; v1 stays the accepted rule until then)** — v1 holds, except for how JWKS fetches start and are shared. At most one JWKS fetch is in flight. A request needs a fetch when the cache is empty or its 3,600 s have ended (it is then discarded, as under v1), or when its ID token carries a `kid` that no cached usable key matches. When a fetch is needed and one is in flight, the request awaits that fetch, then uses the cache as that fetch left it and starts no fetch of its own, even if a `kid` still matches nothing. When a fetch is needed and none is in flight, a fetch starts only if no fetch started in the last 60 s; otherwise the request uses the cache as it is, and an empty cache rejects the ID token. A fetch's start is the clock reading of the request that starts it; the 60 s throttle and the 3,600 s lifetime of the key set it stores both count from it. A fetch that rejects, or answers other than 200, leaves the cache as it was, for the request that started it and for every request awaiting it. A request whose cache was empty and whose `kid` still matches nothing after the fetch it started or awaited starts no second fetch. A request whose cached keys match its token uses them at once, even while a fetch is in flight.

## Rationale

The upstream ID token is the only identity evidence; a weak check would let anyone mint proxy tokens. Source: [F-010 v1](../features/F-010-oauth-proxy.md), AC-14.

## Examples

- **Given** an ID token with a wrong `nonce`
  **When** the callback verifies it
  **Then** 302 with `error=server_error` and no code.
- **Given** an ID token with an unknown `kid` 61 s after the last JWKS fetch
  **When** the callback verifies it
  **Then** the JWKS is fetched once more.
- **Given** an empty JWKS cache and a pending fetch (v2)
  **When** a second callback needs the keys
  **Then** it awaits that fetch and succeeds with one JWKS request in total
- **Given** a fetch that started at `T` and failed (v2)
  **When** a callback arrives at `T + 60` s − 1 ms, then at `T + 60` s
  **Then** no request, then one request
