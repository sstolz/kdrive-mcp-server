## Rule

`createOAuthProxy` takes the effective proxy configuration of F-002 (`publicUrl`, `oauthIssuer`, `oauthAudience`, `oauthAllowedSubjects`, `oauthAllowedEmails`, `oauthUpstreamClientId`, upstream client secret, signing-key bytes, `oauthAllowedRedirectUris`) and injected ports (clock, random bytes, upstream OIDC port, optional logger) and performs no network, file or clock I/O while constructing. The signing-key bytes must be one PEM `PRIVATE KEY` (PKCS#8) block holding an EC P-256 private key; any other content, curve or key type raises `AuthConfigurationError` with a fixed message that echoes no key material. The key's `kid` is the RFC 7638 SHA-256 JWK thumbprint of its public key, base64url without padding, so the same key file always yields the same `kid`. The proxy issuer is the canonical public URL (F-002 canonical form) and the upstream issuer is the canonical `oauthIssuer`. `createProductionPorts()` returns the clock `() => new Date()` and `node:crypto` `randomBytes` as the random source.

Version 2 (F-019 v1, #103; accepted on main `68209fe`, 2026-11-11): `createOAuthProxy` also takes an optional state-store port (opened, checked, purged and loaded beforehand by `openOAuthStateStore`); construction still performs no network or clock I/O and reads state only through the store port.

## Rationale

Construction must stay side-effect free and the signing key must be deterministic so tokens survive a restart with the same key file. Source: [F-010 v1](../features/F-010-oauth-proxy.md), AC-01.

## Examples

- **Given** a synthetic PKCS#8 P-256 PEM
  **When** the proxy is constructed twice
  **Then** no port is called and both `kid` values equal the RFC 7638 thumbprint.
- **Given** a P-384, RSA or Ed25519 key, a public-key PEM or random bytes
  **When** the proxy is constructed
  **Then** `AuthConfigurationError` is raised with one fixed message that contains no input byte.
