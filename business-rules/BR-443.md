## Rule

`WindowLimiter.take` (`src/http/limits.ts`), each time it opens a new window for a key (no window for that key, or its window has ended: `now >= start + windowMs`), first removes every entry whose window has ended at `now`; a `take` that counts into or refuses from a live window removes nothing. After a `take` that opens a window, the limiter holds only entries whose window is live at that `take`'s `now`; after a `take` that counts into or refuses from a live window, the entry count is unchanged. Pruning changes no admission or `Retry-After` result of BR-161 or BR-325. An aggregate `size` accessor (test evidence only, exposing no key) reports the entry count.

## Rationale

The per-identity MCP window (BR-161) and the `/healthz` windows (BR-325) otherwise keep one entry per key forever, so memory grows with every identity ever seen. Pruning on window creation needs no timer, like `OAuthWindowLimiter` (BR-162 v3). Source: [F-053 v1](../features/F-053-http-lifecycle-hardening.md), D-2.

## Examples

- **Given** a limiter (limit 120, 60,000 ms) with windows for keys A and B opened at t=0
  **When** key C takes at t=60,000
  **Then** `size` is 1.
- **Given** a fresh limiter where A takes at t=0 and B at t=30,000
  **When** B takes at t=60,000 (A's window has ended, B's is live)
  **Then** `size` is still 2.
- **Given** 1,000 distinct keys each taking once over more than 60,000 ms
  **When** each take completes
  **Then** `size` never exceeds the keys with a live window, and the BR-161 121st-request refusal and `Retry-After` are unchanged.
