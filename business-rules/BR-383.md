# BR-383 — First-in first-out hand-off, never two invocations at once

## Rule

When the slot is released, it is assigned in the same synchronous step (before any microtask or timer runs) to the oldest call still waiting whose monotonic wait is below 12,000 ms at that moment; a waiter at or past 12,000 ms is refused under BR-382 and skipped. Calls take the slot in the order they joined, and no invocation (read, resource read or gate run) starts until the previous one has settled, so writes never overlap any other invocation. In that same step the taker's wait timer is cleared and its wait abort listener is replaced by the invocation's cancel listener, so no abort can fall between them; the taker then re-runs the closed and aborted checks, and if either holds it returns `ACCESS_DENIED` with zero kDrive requests and zero audit records and the slot passes on in the same way.

## Rationale

Strict order prevents starvation, and one-at-a-time execution keeps writes serialized with one outstanding mutation (F-026 D-1, D-5). Source: [F-026 v1](../features/F-026-bounded-invocation-queue.md).

## Examples

- **Given** a `kdrive_rename` whose mutator answers after 2,000 ms
  **When** a `kdrive_info` starts at 100 ms
  **Then** the read makes no request until the rename result is returned
- **Given** a `kdrive_info` answering after 2,000 ms
  **When** a `kdrive_rename` starts at 100 ms
  **Then** its intent append and attempt happen only after the read settled
- **Given** four waiting calls joined as read, resource read, `mutate`, read
  **When** each running invocation settles
  **Then** they take the slot in that order, and a call arriving at a release joins the tail
- **Given** a running read and waiters A and B, A's signal aborted in the same step as the release
  **When** the read settles
  **Then** A returns `ACCESS_DENIED` with zero requests and B takes the slot
