## Rule

The callback handler takes the query parameters and the `Cookie` header and checks, in this order: (1) a repeated parameter, or an absent, unknown, expired or already-presented `state`, or a cookie mismatch (BR-130) yields a 400 HTML error page and no redirect; the flow is consumed on its first presentation whatever the outcome; (2) when the upstream metadata advertises `authorization_response_iss_parameter_supported` `true` `iss` is required, and when `iss` is present it must equal the upstream issuer, else a client redirect with `error=server_error`; (3) `code` and `error` together, or neither, or an empty `code`, produce a client redirect with `error=server_error`; (4) an upstream `error` produces a client redirect with `error=access_denied` when it is `access_denied`, else `server_error`, and upstream `error_description` and `error_uri` are never forwarded; (5) otherwise the proxy exchanges the code at the upstream token endpoint with `grant_type=authorization_code`, the code, the callback `redirect_uri` and the PKCE verifier, authenticated per BR-131 (Basic components form-urlencoded before Base64, RFC 6749 §2.3.1). Steps 2–4 make no upstream request. A failed or non-200 exchange, a missing `id_token` or a `token_type` other than `Bearer` (case-insensitive) produces a client redirect with `error=server_error`.

## Rationale

The callback is the attack surface for mix-up and replay; strict ordering and fixed error mapping keep it safe. Source: [F-010 v1](../features/F-010-oauth-proxy.md), AC-12, AC-13.

## Examples

- **Given** a valid flow
  **When** the callback arrives with an altered `state`
  **Then** 400 HTML, no redirect and no upstream exchange.
- **Given** a valid flow
  **When** the upstream returns `error=access_denied` with a description
  **Then** 302 with `error=access_denied` and no description.
