## Rule

The navigation controller exposes `mutate(tool, operation, identity, signal, payload?)`, the only entry point for a gate run: it runs the gate inside `perform` with `paged:false`, waits in the shared invocation queue (BR-380) when another invocation holds the slot or a call is waiting, answers `SERVER_BUSY` with zero records only when the queue is full (BR-381) or the wait times out (BR-382), and `ACCESS_DENIED` with zero records when its signal aborts or the controller closes while it waits (BR-385, BR-386), and returns the gate result (BR-255) as its value. When a gate run executes through the policy `execute` dependency inside that invocation, the navigation 10,000 ms deadline, cancellation, session close, dependency-call cap and output checks apply only until the gate starts the intent append. From then on the navigation controller does not abort, race, time out or discard the `execute` call, and the caller receives the gate result (BR-255), never a navigation `REQUEST_TIMEOUT`, `ACCESS_DENIED` or `LIMIT_EXCEEDED` code; the navigation abort signal reaches the gate only as a BR-250 cancellation; a gate result whose serialization exceeds the navigation output bound is returned without its `value` member; and the navigation slot stays held (other calls wait under BR-380, or get `SERVER_BUSY` under BR-381 and BR-382) until the gate result is returned. After a client cancellation the MCP response may be dropped (MCP cancellation semantics); the audit outcome is then the authority.

## Rationale

A navigation timeout must never report a performed write as failed (D-16-13). Source: [F-016 v1](../features/F-016-mutation-audit-gate.md); v2 lets a parallel call wait instead of failing (#16): [F-026 v1](../features/F-026-bounded-invocation-queue.md).

## Examples

- **Given** a mutator answering 200 after 12,000 ms
  **When** `mutate` runs
  **Then** the caller gets `succeeded`, and a read that joined the queue at 1,000 ms makes no request until then and then succeeds (v2; v1: the read gets `SERVER_BUSY`)
- **Given** the navigation deadline firing before the intent append
  **When** `mutate` runs
  **Then** the caller gets `REQUEST_TIMEOUT` with zero records
- **Given** a gate run past its intent append whose mutator answers after 20,000 ms, and a second `mutate` that joined the queue at 1,000 ms (v2)
  **When** 13,000 ms have passed
  **Then** the second `mutate` returns `SERVER_BUSY` with zero records and zero attempts
