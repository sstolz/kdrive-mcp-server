# BR-264 — Original-trash evidence

## Rule

`inspect(target, "original-trash")` issues one `GET` on the trash-metadata route and, when the item's `status` is `trashed`, then one `GET` on the item route for its `parent_id`; it returns complete original-trash evidence (location `original-trash`, lifecycle `trashed`, `treeRootId` equal to the target ID, the trashed item's ID, type and name, `path` equal to the trash `path`, and as original parent chain the normalized live chain of the former parent followed by the former parent) only when that former parent normalizes as a complete live directory (BR-198, BR-199 v2) and the trash `path` equals the former parent's path joined with the item's name.

## Rationale

Trash metadata has no ancestor identities (Stage A T1); the live former parent supplies them and must agree with the trash path (D-17-3). Source: [F-017 v1](../features/F-017-controlled-tree-mutations.md).

## Examples

- **Given** trash metadata `{status:"trashed", parent_id:11, path:"/Private/docs/gone.txt"}` and a live folder 11 at `/Private/docs`
  **When** `inspect` runs
  **Then** it returns complete evidence after exactly two GETs
- **Given** a directly trashed item whose former parent is root 1 and whose path is `/gone.txt`
  **When** `inspect` runs
  **Then** the parent chain is the root sentinel only
