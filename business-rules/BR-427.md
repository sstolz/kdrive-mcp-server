# BR-427 — Fresh proof of configured-root non-ancestry

## Rule

**v1 (F-041 v1, #47; accepted on main `448a48f`)**

Before authorizing a live folder source for `trash`, `rename` or `move`,
the policy requires fresh, complete and mutually consistent live evidence
that the source is not a strict ancestor of any configured root in the
same drive; otherwise it refuses through the existing `ACCESS_DENIED`
dispatch/gate result, with the BR-246 denied audit attempt and no mutation.

Inspect configured IDs, not configuration-time paths. The drive-qualified
source ID in a root's validated complete parent chain proves strict
ancestry; current canonical paths must agree with that identity relationship.
Retain exact case and Unicode, component boundaries and the existing
4,096-byte path grammar: invalid trailing slashes or inconsistent spellings
are incomplete evidence, not normalized into authority. Missing, inaccessible,
trashed, wrong-type, wrong-identity, cyclic, incomplete or contradictory
root evidence is unknown and refuses. A direct configured-root source
already refuses under BR-278 without needing evidence.

Reuse at most one inspection per distinct identity inside the same decision;
never reuse preflight ancestry or cross-invocation ancestry. Root 1 has no
strict ancestors and needs no added inspection. Other drives cannot match
and need no ancestry reads. All relevant roots must be excluded unless the
operation already refuses. Use the existing bounded inspection and
observation path, no descendant enumeration or unbounded parent walk.
Existing invocation interruption/admission results retain precedence and
can never authorize execution. No new root reads apply to other operation
kinds, file sources or move destinations as such. Deny patterns cannot
remove configured roots from the protected set.

## Rationale

Fresh provider ID chains follow the configured identity after external
rename/move, while stale paths and incomplete visibility cannot prove a
negative relationship. The deliberate availability cost is that an
inaccessible root blocks otherwise eligible folder structural mutations in
its drive. Source: [F-041 v1](../features/F-041-configured-root-ancestors.md),
#47 lot E decision.

## Examples

- **Given** root `101:40` is now `/D/R` after moving from `/A/B/R`
  **When** a structural operation targets D
  **Then** fresh root evidence proves D is protected; a later operation on
  former parent B is permitted if all other checks pass. Maps to
  `TestBR427_AC07_renamed_and_moved_roots_use_current_id_ancestry`.
- **Given** configured root 40 cannot be inspected live
  **When** a structural operation targets apparent sibling S
  **Then** `ACCESS_DENIED`, zero mutation requests and one attempted denied
  record. Maps to `TestBR427_AC05_unknown_root_ancestry_fails_closed`.
- **Given** source `/A` and root `/AB/R` with a complete chain not containing A
  **When** ancestry is checked
  **Then** A is not an ancestor; valid `/a` and NFC/NFD siblings are likewise
  distinct. An inconsistent chain or `/A/` path refuses instead. Maps to
  `TestBR427_AC06_ids_and_exact_canonical_paths_agree`.
- **Given** every same-drive root is outside S and only another drive's
  root is inaccessible
  **When** S is renamed
  **Then** that other drive is not inspected and the permitted operation
  succeeds. A root in S's drive with unknown ancestry refuses instead.
  Maps to `TestBR427_AC08_all_same_drive_roots_checked_once_without_tree_walk`.
