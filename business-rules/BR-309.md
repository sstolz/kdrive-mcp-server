# BR-309 — CIMD cache, concurrency and cancellation

## Rule

Resolution results are cached in memory only, keyed by URL, at most 100 entries. A valid document is fresh for 60 s when `Cache-Control` has a `no-store` or `no-cache` directive; otherwise for its `max-age` clamped to 60–3,600 s; otherwise for 300 s. Parsing: the `Cache-Control` field lines are joined with commas and split into comma-separated directives, each trimmed of spaces and tabs, the name (before any `=`) compared case-insensitively and the value taken after the first `=`; `max-age` is the value of the first `max-age` directive whose value is 1–10 ASCII digits (no quotes, sign or other character); a field with no such directive has no `max-age`; every other directive (`public`, `private`, `s-maxage`, `must-revalidate`, `immutable`, unknown ones) and `Expires` are ignored. A failure is never cached. While fresh, an entry is used without fetching. After it expires it is kept for 3,600 s more as a stale entry that is used only when the refetch fails transiently; a terminal failure deletes it. When a new entry would exceed 100, the entry that would be discarded first (stale end for stale entries, freshness end plus 3,600 s otherwise) is evicted. At most one fetch per URL is in flight (concurrent authorization requests for that URL share it) and at most 4 fetches in total; an authorization request that would start a fifth gets the 503 HTML error page without fetching. At the 5,000 ms deadline or at any failure, the proxy calls the resolver's `cancel()`, destroys the request and its socket, and frees the slot at that moment. A transient failure with no usable stale entry gives the 503 HTML error page; a terminal failure gives the 400 HTML error page; neither redirects. When the HTTP server's `close()` closes the handler (BR-169 v3 step (2)), the proxy cancels every in-flight fetch in the same way (resolver `cancel()`, request and socket destroyed, slot freed), and every authorization request waiting on one gets the 503 HTML error page without redirect, settled in that step, and creates no pending consent.

## Rationale

Caching bounds fetches, stale use keeps clients working through transient outages, and the concurrency and deadline bounds keep an unauthenticated route from holding resources (D-5, D-6). Source: [F-028 v2](../features/F-028-client-id-metadata-documents.md).

## Examples

- **Given** a document with `Cache-Control: max-age=86400`
  **When** authorize runs again
  **Then** the port is called again exactly after 3,600 s
- **Given** four distinct URLs pending
  **When** a fifth URL is requested
  **Then** the 503 page, `client_metadata_refused` `busy`, and no call
- **Given** a pending fetch
  **When** the HTTP server closes
  **Then** the resolver is cancelled, the socket destroyed and the request gets the 503 page
