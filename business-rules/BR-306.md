# BR-306 — CIMD fetch

## Rule

The proxy fetches an acceptable CIMD client ID with one HTTPS `GET` to that exact URL whose only request headers are `Host`, `Accept: application/json`, `User-Agent: kdrive-mcp-server` (fixed, no version or host detail) and `Connection: close`: no `Accept-Encoding`, no cookie, no `Authorization` header and no other credential. It verifies the certificate for the URL host against Node's default CA store (the bundled roots plus any `NODE_EXTRA_CA_CERTS`), on the URL port (443 when absent). The request uses a dedicated `https.Agent` created without `proxyEnv`, so `NODE_USE_ENV_PROXY`, `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY` have no effect on it, with keep-alive off and `rejectUnauthorized: true` set explicitly, so `NODE_TLS_REJECT_UNAUTHORIZED=0` cannot disable verification (as for the kDrive transport, BR-191 and BR-216 v2). The host is resolved exactly once, never through `dns.lookup` (getaddrinfo on the libuv threadpool), but through a `dns.promises.Resolver` (c-ares, outside the threadpool) created for this fetch with `timeout` 2,000 ms and `tries` 2, which queries `resolve4` and `resolve6` in parallel; the answer is the union of both. A query that ends with `ENODATA` or `ENOTFOUND` contributes no address; any other query error fails the fetch as `resolution`. When the 5,000 ms deadline passes the proxy calls the resolver's `cancel()`, so no query outlives the fetch. Every returned address is checked under BR-307, and if any is blocked, or the union is empty, the fetch fails without connecting. Otherwise the agent's `lookup` returns, from memory, every checked address and only those (the `all` form, `resolve4` answers first, then `resolve6` answers, each in answer order), and the connection is made with `autoSelectFamily` true, so Node's connection attempts fall over from one checked address to the next until one connects or the 5,000 ms deadline passes; no second resolution happens for this fetch. The fetch succeeds only with status 200 (no redirect is followed; every other status fails), a `Content-Type` media type `application/json` or `application/<name>+json` (parameters ignored, case-insensitive), no `Content-Encoding` other than `identity` (the body is never decompressed; any other coding is a terminal `content_type` failure), a body of at most 5,120 bytes (reading stops and fails at the 5,121st byte, whatever `Content-Length` says) and completion within 5,000 ms from the start of the resolution. A failure is transient when the resolution fails, the connection or TLS handshake does not complete for a reason other than a certificate verification failure, the 5,000 ms elapse, or the status is 429 or 5xx; every other failure is terminal.

## Rationale

The fetch is an SSRF primitive and must not be steerable by DNS, proxies, redirects, compression or slow peers, nor exhaust the libuv threadpool (D-8). Source: [F-028 v2](../features/F-028-client-id-metadata-documents.md).

## Examples

- **Given** a server answering 302, 404, `text/html` or `Content-Encoding: gzip`
  **When** the production port fetches the URL
  **Then** a terminal failure (`status` or `content_type`) without following any redirect
- **Given** a body of 5,121 bytes, also with `Content-Length: 100`
  **When** the production port reads it
  **Then** a terminal `size` failure; 5,120 bytes are accepted
- **Given** a child with `NODE_USE_ENV_PROXY=1`, `HTTPS_PROXY` and `NODE_TLS_REJECT_UNAUTHORIZED=0`
  **When** the port fetches a trusted and an untrusted server
  **Then** the trusted fetch succeeds, the untrusted one fails as `certificate` and the proxy receives no connection
