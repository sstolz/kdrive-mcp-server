# BR-412 — Cross-reference chain

## Rule

Cross-reference data is read only from the last `startxref` offset and the chain it starts, with no scan for objects and no repair. Each section is either a classic `xref` table with a trailer, or a stream object whose dictionary has `/Type /XRef`, a direct `/Size`, a `/W` of three integers each 0–8 and an optional `/Index` of start/count pairs. A classic trailer's `/XRefStm` and every section's `/Prev` are followed; at most 32 sections are read and a section offset seen twice is a cycle. For each object number the newest section that lists it wins (a section's `/XRefStm` entries rank below its own table, above its `/Prev`). The newest trailer gives `/Root`; `/Size` of every section is at most 65,536 and every listed object number is below its section's `/Size`. A decoded cross-reference stream holds exactly the listed entry count times the sum of `/W` bytes; a type 0 entry is free, type 1 gives a byte offset and generation, type 2 gives an object stream number and index, and any other type is free.

## Rationale

Cross-reference streams (PDF 1.5+), hybrid files, incremental updates and linearized files are the default output of common generators; the F-009 profile refused them (F-034 S05–S07). Reading them by offset only, with a bounded cycle-checked chain, keeps the interpretation deterministic and bounded. Source: [F-034 v1](../features/F-034-pdf-extraction-profile.md).

## Examples

- **Given** a file whose second revision (`/Prev`) replaces page 1's content
  **When** page 1 is read
  **Then** the second revision's text
- **Given** a `/Prev` chain A→B→A
  **When** page 1 is read
  **Then** `CONTENT_UNAVAILABLE` before PDF.js
- **Given** 33 cross-reference sections
  **When** page 1 is read
  **Then** `LIMIT_EXCEEDED` before PDF.js
