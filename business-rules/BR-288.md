# BR-288 — Upload documentation

## Rule

The README and `SECURITY.md` state that `kdrive_upload` exists only in `write` and `share` modes, its 524,288-byte bound (and the lower 262,144-byte HTTP body limit), that `overwrite:false` asks kDrive to refuse an existing same-name file as observed behaviour (9/9 samples, checked at completion) and not a guarantee, that names are case-sensitive, that `overwrite:true` requires `file_id` and replaces content in place under the same ID, that an `uncertain` upload is never replayed, that received-share uploads stay refused even with `KDRIVE_MCP_SHARED_WRITE=1`, the decoded-bytes bound versus the transport limit (HTTP 413; stdio termination with `STDIO_INPUT_FAILED`, the in-flight outcome recorded but its tool result not delivered), that base64 is the reliable form for large or non-ASCII content, and residual risks R-18-1–R-18-5.

Since v2: the README and `SECURITY.md` also state the NFC rule for `kdrive_upload`, `kdrive_create_folder` and `kdrive_rename`; that deny patterns match exact stored code points (NFC form for new names, stored form kept for existing non-NFC names); R-18-3 as an accepted risk; and R-18-5 as restated in F-018 v2.

## Rationale

Operators and clients must know what the no-overwrite default really guarantees. Source: [F-018 v1](../features/F-018-upload.md).
