# BR-435 — Redacted deny-pattern startup warning

## Rule

After complete successful preflight and before audit-sink opening or either
transport's activation, startup offers exactly one best-effort stderr JSON
object plus LF per BR-434 v1 classification, in ascending selected-list index:

```json
{
  "event": "deny_pattern_root_warning",
  "level": "warn",
  "setting": "deny",
  "pattern_index": 0,
  "reason": "outside_configured_roots"
}
```

Only `pattern_index` varies: it is the zero-based index in the effective selected
deny list. All other values and the exact field set are fixed. At most 256
warnings are offered. The event includes no input value, path, identifier,
credential, timestamp, exception or configuration dump. It is independent of
upstream-event rate windows and changes neither startup eligibility nor
filtering. A throwing warning write does not refuse startup or add a flush wait.

Both stdio and HTTP use this shape. Warnings never enter MCP stdout, HTTP
responses or mutation audit records. Failed preflight, failed local validation,
local-only loading, `--help` and `--version` emit none. Sessions, tools and
shutdown emit no repeats. A later unrelated startup failure may follow warnings.

## Rationale

Let operators find a potentially mistaken entry in their selected configuration
without logging its contents or changing its enforcement effects.

## Examples

- **Given** root `/Private/Documents` and selected deny
  `[/Documents/Confidential/**, /Private/Documents/**, /Other/**]`
  **When** preflight succeeds
  **Then** indices `0` and `2` warn in that order before transport activation.
- **Given** a warning candidate and a later unresolved root
  **When** preflight fails
  **Then** only the existing sanitized configuration error is emitted.
- **Given** 256 incompatible selected entries
  **When** preflight succeeds
  **Then** exactly 256 warning writes are offered, indexed `0` through `255`.
