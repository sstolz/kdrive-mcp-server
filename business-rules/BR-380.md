# BR-380 — Calls wait in a per-session queue instead of being refused

## Rule

Each navigation controller (one per MCP session, stdio or HTTP) runs at most one invocation at a time. A tool call, resource read or `mutate` call that passes the existing closed and aborted checks, and arrives while an invocation holds the slot or while any call is waiting, joins the tail of that controller's wait queue and makes no kDrive request, dependency call or audit append while it waits.

## Rationale

MCP clients send parallel calls in one session (claude.ai sent two `kdrive_info` calls at once in the `0.6.0-beta.1` smoke test, #16); refusing the second lost a correct read. Waiting keeps execution serialized. Source: [F-026 v1](../features/F-026-bounded-invocation-queue.md).

## Examples

- **Given** an idle session
  **When** `kdrive_info` and `kdrive_list` start in the same tick
  **Then** both succeed and `kdrive_list` makes its first request only after `kdrive_info` settled
- **Given** the same calls started in the reverse order
  **When** both run
  **Then** both succeed and `kdrive_info` starts only after `kdrive_list` settled
- **Given** two HTTP sessions each holding a never-answering read
  **When** a call arrives on the second session
  **Then** it waits only behind the second session's read
