# BR-409 — Language switch replaces the pending consent

## Rule

When an authorize request reaches the point of creating a pending consent, carries a valid `lang` (BR-405) and a well-formed binding cookie (BR-130), and a live pending consent exists with the same cookie hash and a pending request equal in every field (`clientId`, `redirectUri`, `state`, `codeChallenge`, `resource`, `cimdGrants`; strings compare with `===`; `state` and `cimdGrants` are equal when both are absent, or both present with the same values, `cimdGrants` in the same order), the oldest such live consent in insertion order (chosen after the expiry purge) is deleted before the BR-142 store-bound check and the new one is created; at most one consent is replaced per request. The replaced identifier is then unknown: a form posted from the earlier page gets the `consent` error page. Without a valid `lang` or without the cookie, behaviour is unchanged (a new consent is added). Accepted residual risk: the cookie is `SameSite=Lax`, so a cross-site link that copies a victim's full authorize request, including the exact `state` and `code_challenge`, and adds `lang` deletes the victim's pending consent; the victim gets a fresh consent page for the same request, a nuisance only.

## Rationale

A switch must not leave a stale pending consent behind nor be refused on a full store (F-031 D-3). Source: [F-031 v1](../features/F-031-oauth-proxy-page-languages.md).

## Examples

- **Given** a consent page obtained with cookie C
  **When** its switcher link is followed with C
  **Then** the pending-consent count is unchanged and the earlier identifier gets the 400 `consent` page
- **Given** the same switch without the cookie, or with another well-formed cookie
  **When** authorize answers
  **Then** a consent is added and none deleted
- **Given** a store of 1,000 pending consents including that consent
  **When** the switch is followed with C
  **Then** the consent page is shown
