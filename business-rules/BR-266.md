# BR-266 — One new connection per mutation request

## Rule

Each mutation request opens a new TLS connection through the BR-191 address policy and the BR-216 v2 `connect`, carries no other request, sends `Connection: close` and an explicit `Content-Length`, sends a body only for `create` and `rename` (`Content-Type: application/json`, the bytes of `JSON.stringify({name})`) and for `upload-new` and `replace` (exactly the payload bytes, `Content-Type: application/octet-stream`, `Content-Length` equal to their count, 0 included), and never follows a redirect.

## Rationale

A dedicated connection makes the not-sent boundary exact (D-17-5); no redirect can move the bearer token. Source: [F-017 v1](../features/F-017-controlled-tree-mutations.md).

## Examples

- **Given** two successive trash runs
  **When** they complete
  **Then** the server saw two connections with one request each
- **Given** a 302 answer to a rename
  **When** the run ends
  **Then** no second request is made and the result is `uncertain`
