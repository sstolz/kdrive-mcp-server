## Rule

v3 (F-028 v1, #3, pending acceptance; v2 stays the accepted rule until then): for a CIMD client ID the authorize handler checks, in this order and each before any fetch: (1) a repeated parameter; (2) BR-305 acceptability; (3) a `redirect_uri` that is absent or matches no entry of the current `oauthAllowedRedirectUris` under BR-126. Each refusal is the 400 HTML error page, no redirect. Only then is the client resolved under BR-306–BR-309, and the `redirect_uri` must match under BR-126 a redirect URI kept from the document; otherwise the 400 page, no redirect. Registered clients keep today's order. The authorize handler becomes asynchronous: the BR-299 latch is checked again after the resolution, and a latched store answers the 503 page and creates no pending consent. The event of each refusal follows Contract details "Authorization refusal events".

The authorize handler takes the query parameters and the `Cookie` header. A repeated parameter, an unknown `client_id`, or a `redirect_uri` that is absent or matches none of the client's registered URIs under BR-126 yields a 400 HTML error page and no redirect; `redirect_uri` is required even for a client with one registered URI. A `state` is valid when absent, or when it is 1–1,024 bytes without control characters. With a known client and matching `redirect_uri`, the first defect in this order produces a client redirect with `error`: `response_type` absent or other than `code` → `unsupported_response_type`; invalid `state` → `invalid_request`; `code_challenge` absent or not exactly 43 base64url characters, or `code_challenge_method` absent or other than `S256` → `invalid_request`; `resource` absent or not byte-identical to the audience → `invalid_target`. `scope` and unknown parameters are ignored. A valid request returns the consent page (BR-129).

Version 2 (F-019 v1, #103; accepted on main `68209fe`, 2026-11-11): the `redirect_uri` matches only when it matches under BR-126 both a registered URI of the client and an entry of the current `oauthAllowedRedirectUris`, otherwise the 400 HTML error page with no redirect; the handler is otherwise unchanged.

## Rationale

An unverified redirect target must never receive a redirect, and every defect is reported to a verified client with RFC 9207 `iss`. Source: [F-010 v1](../features/F-010-oauth-proxy.md), AC-06, AC-07.

## Examples

- **Given** an unknown `client_id`
  **When** the authorization request arrives
  **Then** a 400 HTML page without `Location`.
- **Given** a known client and a 1,025-byte `state`
  **When** the authorization request arrives
  **Then** 302 with `error=invalid_request`, `iss` and no `state`.
- **Given** a listed CIMD client ID with a repeated parameter, an absent `redirect_uri` or one outside the allowlist
  **When** authorize runs
  **Then** the 400 page and the fetch port is not called (v3)
- **Given** a CIMD fetch pending while the store latches
  **When** the fetch then succeeds
  **Then** the 503 page and no pending consent (v3)
