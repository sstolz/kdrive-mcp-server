## Rule

Authorization uses the `(iss, sub)` subject allowlist and the optional exact email allowlist, an email matching only when `email_verified` is the boolean `true`; an authenticated token matching neither list is rejected with status 403 reason `identity`, and creating a validator with both lists empty is a configuration error. When the validator is created with an `upstreamIssuer` (v2, proxy-issued tokens), a token whose `upstream_iss` claim is absent or differs from it is rejected with 401 `issuer` right after the `iss` check, the subject allowlist is matched against (`upstreamIssuer`, `sub`) and the success identity is (`upstreamIssuer`, `sub`); without it the v1 behaviour is unchanged.

## Rationale

Authentication by the provider does not authorize every account it knows; only listed owners reach the server. Source: [F-008 v1](../features/F-008-oidc-qualification.md), AC-11, AC-12.

## Examples

- **Given** an unlisted subject whose listed email has `email_verified` `"true"` (string).
  **When** it is validated.
  **Then** it is rejected with 403 `identity`.
- **Given** the same token with `email_verified` `true`.
  **When** it is validated.
  **Then** it is accepted.
- **Given** a validator with `upstreamIssuer` `https://upstream.test` and subject (`https://upstream.test`, `user-1`).
  **When** a token with `upstream_iss` `https://upstream.test` and `sub` `user-1` is validated.
  **Then** it is accepted with identity (`https://upstream.test`, `user-1`).
- **Given** the same validator.
  **When** a token without `upstream_iss` is validated.
  **Then** it is rejected with 401 `issuer`.
- **Given** both allowlists empty.
  **When** a validator is created.
  **Then** creation throws a configuration error.
