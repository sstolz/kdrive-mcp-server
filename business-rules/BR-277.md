# BR-277 — Write tool documentation

## Rule

The README and `SECURITY.md` state that the five tools exist only in `write` and `share` modes, that this server never requests permanent deletion (BR-270), that restore returns an item only to its former parent when that parent is live and authorized and refuses otherwise, that a folder restore is refused when deny patterns are configured, that received-share writes stay refused, that configured roots cannot be trashed, renamed or moved (BR-278), and that a check-then-act window remains (SPEC §10.6), including a former parent trashed between the check and the restore (when that former parent is a configured root, the folder the server recreates has a new ID outside every configured root), and an item trashed between the check and a trash request, whose effect under `DELETE /2/drive/{d}/files/{f}` is unmeasured. They also state residual risk R-17-1: restore authorizes the former parent's current path, so an item trashed under a denied folder that is renamed or moved out of the deny patterns outside this server can be restored. The implementation PR includes R-17-1; the records PR after acceptance keeps it when Acceptance step 6 shows `succeeded` (trash `path` recomputed) and narrows it to "not observed on the measured server" when step 6 shows `denied` (snapshot); a `succeeded` restore that lands anywhere other than under `G2` with the same ID, or that recreates `G`, fails acceptance; any other step-6 result keeps R-17-1 unchanged and is recorded as unmeasured. They also state residual risk R-17-2: BR-278 protects only a configured root targeted directly, so with nested roots, trashing, renaming or moving an authorized folder of an outer root that contains an inner configured root also affects that inner root, and with nonempty denies the trashed folder cannot be restored through this server (D-17-4).

## Rationale

Operators must know the limits and residual risks of the first write tools. Source: [F-017 v1](../features/F-017-controlled-tree-mutations.md).
