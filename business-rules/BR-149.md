# BR-149 — The sonar-pr CI job

## Rule

v2 (F-015 v1, pending acceptance; v1 below stays the accepted rule until then): v1 holds with these changes. `sonar-pr` runs on the BR-225 label array, needs `changes`, `lint`, `format`, `typecheck`, `test` and `build`, and its job `if` is exactly `github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository && needs.changes.outputs.heavy != 'false'`; its steps and step conditions are unchanged. A separate job `fork-refusal` on `ubuntu-24.04` has `permissions: contents: read`, `timeout-minutes: 5`, no `needs`, no checkout, the job `if` exactly `github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name != github.repository`, and one step whose `run` is the BR-149 fork-refusal text, so a fork PR never has a successful run. Besides step `if` expressions and the `SONAR_PR_HEAD_REPOSITORY` step `env`, the head repository appears only in the job `if` of `sonar-pr`, `fork-refusal`, `changes` and `ci-result`, exactly as written here and in BR-227; never in a `run` script or any other `env`.

The CI workflow has a `sonar-pr` job that runs only for `pull_request` events
into `main`, needs `lint`, `format`, `typecheck`, `test` and `build`, has
`timeout-minutes: 15`, and uses concurrency group `sonar-kdrive-mcp-server-pr`
with `cancel-in-progress: false`. Its checkout uses the default pull-request
merge ref, `fetch-depth: 0` and `persist-credentials: false`. The head
repository appears only in step `if` expressions and in the
`SONAR_PR_HEAD_REPOSITORY` step `env`, never in a `run` script; an empty value
counts as foreign. For a foreign head repository, its only executed `run` step
fails with a fixed message and references no secret. For the same repository,
when `vars.SONAR_ENABLED` is not `true`, it prints a fixed "PR Quality Gate
disabled" notice; when it is `true`, it runs the BR-151 pristine export,
`make setup`, the BR-151 comparison, then `make sonar-pr` with exactly
`SONAR_ENABLED`, `SONAR_HOST_URL`, `SONAR_TOKEN` from `secrets.SONAR_PR_TOKEN`,
`SONAR_PRISTINE_TAR` and `SONAR_PR_HEAD_REPOSITORY`. The workflow never uses
`pull_request_target`, and no workflow-level or job-level `env` holds a secret.

## Rationale

Fork code must never receive a secret, and a skipped job would count as passing, so forks fail closed. Source: [F-011 v1](../features/F-011-pre-merge-quality-gates.md).

## Examples

- **E-01 — Given** a fork head repository
  **When** the `sonar-pr` step conditions are evaluated
  **Then** only the refusal `run` step executes and no executed step references a secret.
- **E-02 — Given** the same repository with `SONAR_ENABLED=true`
  **When** the step conditions are evaluated
  **Then** the export, setup, comparison and `make sonar-pr` steps execute.
- **E-03 — Given** a workflow giving the PR job `secrets.SONAR_TOKEN`
  **When** the CI policy validator runs
  **Then** it rejects the workflow.
