# BR-429 — Published parameter meaning and validation guidance

## Rule

**v1 (F-042 v1, #42; accepted on main `3b035b8`)**

Every input parameter occurrence and the pages array item publishes the exact F-042 v1 dictionary description at its JSON Schema property/item, consistent with the existing units, omission defaults, bounds and cross-field restrictions.

Source: [F-042 v1](../features/F-042-mcp-tool-descriptions.md), #42 decision.

## Rationale

JSON Schema alone does not expose arbitrary Zod refinements or runtime omission defaults. Explicit descriptions plus observable validation-boundary tests prevent plausible but invalid client calls without changing validation. Received-folder navigation depends on the tool; production received-write refusal depends on the adapter's capability mapping.

## Examples

- **Given** text offset 0 without etag
  **When** the existing read validator runs
  **Then** the combination is accepted and the description says the default offset is 0. Maps to `TestBR429_AC05_cross_field_descriptions_match_validation`.
- **Given** text offset 1 without etag
  **When** the same validator runs
  **Then** INVALID_ARGUMENTS precedes content work and the published offset/etag descriptions state the requirement. Maps to the same test.
- **Given** image with offset 0
  **When** input is validated
  **Then** it is refused, whereas image with none of offset, length, encoding or pages is accepted. Maps to the same test.
- **Given** upload with overwrite true and a valid file_id
  **When** the upload schema validates the arguments
  **Then** the combination passes; the same arguments without file_id fail. Maps to the same test.
- **Given** a 4096-byte and a 4097-byte UTF-8 search query
  **When** argument validation runs
  **Then** the first passes and the second refuses; Q states the byte limit. Maps to `TestBR429_AC06_bounds_and_defaults_match_validation`.
- **Given** a PDF call without pages
  **When** extraction runs
  **Then** selection is [1] and the published description says so. Maps to `TestBR429_AC06_bounds_and_defaults_match_validation`.
- **Given** a valid raw-read fixture and configured maxReadBytes
  **When** length_bytes is omitted or equals maxReadBytes
  **Then** both calls return the same successful result; LB states that remaining bytes and serialized-output budgets can reduce the chunk. Maps to `TestBR429_AC06_bounds_and_defaults_match_validation`.
- **Given** the same raw-read fixture
  **When** length_bytes equals maxReadBytes + 1
  **Then** LIMIT_EXCEEDED precedes policy/content work with zero provider calls; LB describes refusal, not clamping. Maps to the same test.
- **Given** text `A😀B` with ample serialized-output budget
  **When** length is omitted, 1 or 2
  **Then** the result contains three, one or two Unicode code points respectively; L describes a requested maximum subject to remaining text and output budgets. Maps to the same test.
- **Given** a larger bounded text fixture with a serialized-output budget that fits at least one code point
  **When** the requested length does not fit
  **Then** fewer code points are returned, with has_more and next_offset matching the returned count. Maps to the same test.
- **Given** received sharing enabled and a readable received folder in an unconfigured owner drive with complete read/list/search evidence
  **When** recents, my_shared, list and search target that explicit drive_id/folder_id with valid inputs
  **Then** recents and my_shared return bare ACCESS_DENIED while list and search succeed; DR/FSR describe the configured-drive restriction. Maps to the same test.
- **Given** an authorized folder in a configured drive
  **When** recents or my_shared targets it
  **Then** the call succeeds; omitted DR selects the default drive and omitted FSR uses its configured roots. Maps to the same test.
- **Given** the production-adapter BR-257 fixture with sharedWithMe/sharedWrite enabled and provider can_write/can_rename true
  **When** the received folder is renamed after a successful read
  **Then** all normalized received mutation predicates are false, a fresh shared_with_me GET occurs and rename is denied with ACCESS_DENIED and attempts 0, with no intent or mutator call; DW describes this production behavior. Maps to the same test and `TestBR257_a_received_rename_reloads_shared_with_me_and_is_denied` in `tests/mutation-composition.test.ts`.
- **Given** an unconsumed, unevicted returned cursor with unchanged tool, arguments and session in a successful continuation fixture
  **When** it is first used before expiry or reused after consumption
  **Then** the first continuation succeeds and reuse returns INVALID_CURSOR; C describes issued-token behavior without publishing the masked byte guard. Maps to `TestBR429_AC06_bounds_and_defaults_match_validation`.
