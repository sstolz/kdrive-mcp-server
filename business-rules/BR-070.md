## Rule

Every active tool invocation obeys the stated request/output bounds and stops publishing results or starting dependency calls after cancellation, deadline or session close, except a mutation gate run once its intent append has started: from that point the navigation deadline, cancellation, session close and output checks no longer abort, race or replace the run, which is bounded by F-016 (BR-249, BR-250, BR-254, BR-258), and its gate result is published unless the session is closed. The F-005 1,000 ms exit bound after EOF, SIGINT or SIGTERM holds when no gate run is past its intent append start; otherwise the process exits after the gate close (BR-254), bounded by that run's total deadline plus two bounded appends (BR-259; file sink — with the stderr sink the wait also depends on stderr draining, D-16-7). On stdio, a second outbound frame sent while one is being written waits in the bounded outbound queue (BR-388) instead of closing the session; only a queue overflow, a frame above 1,048,576 bytes or a frame not written within 1,000 ms of its write start closes it.

## Rationale

Bounded evidence and stream ownership prevent stalled readers or evidence from retaining a session. Source: [F-005 v1](../features/F-005-stdio-navigation.md), AC-12.

## Examples

- **Given** a request using exactly512 dependency calls and bounded terminal output.
  **When** it completes before deadline.
  **Then** the result succeeds.
- **Given** a513th call, a seventh waiting outbound frame (v3; v2: a second pending send), or stalled output/evidence.
  **When** the bound is reached.
  **Then** the fixed refusal/close occurs, no new work starts and owned resources settle.
- **Given** one stdio frame being written (v3)
  **When** a second frame is sent
  **Then** it waits, both are written in send order and the session stays open (v2: the session closes with `STDIO_OUTPUT_FAILED`)
- **Given** a gate run past its intent append whose mutator answers 200 after 12,000 ms
  **When** the 10,000 ms navigation deadline passes
  **Then** the caller receives `succeeded`, never `REQUEST_TIMEOUT`, and the slot stays held until then
