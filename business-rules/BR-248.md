## Rule

**v1 (F-016 v1; active until v2 acceptance)**

Only an HTTP 429 response is retried, for at most 3 attempts per run; the wait before attempt n+1 is the 429's `Retry-After` value in seconds when it consists of 1–10 ASCII digits, or else 1,000 × 2^(n−1) ms; when the wait exceeds 30 s or would end after the run's total deadline, or the third attempt answers 429, the run ends `failed` with code `RATE_LIMITED`.

**v2 (F-037 v1, #47 lot A, pending acceptance; v1 stays the active rule until then)** — Each admitted mutation run makes at most one upstream attempt. A reply that passes BR-247's reply contract and has HTTP status 429 terminates the run as `failed`, code `RATE_LIMITED`, status `429`, attempts `1`, without waiting for `Retry-After` or calling upstream again. Any subsequent client invocation is a new run subject to all ordinary admission and authorization checks; it inherits no grant from the previous run. BR-243's one intent/outcome pair, BR-249's deadlines, BR-251's uncertainty handling, BR-252's outcome-write failure and BR-255's result fields remain unchanged. No retry-delay field or new audit event is added. Cancellation follows BR-250 v2.

## Rationale

Only a 429 proves the write was not performed (assumption D-16-5); bounded waits keep calls finite. Source: [F-016 v1](../features/F-016-mutation-audit-gate.md).

v2 removes the retry window in which an earlier authorization can become stale. A client resubmission enters the complete current admission and policy path; no idempotency or atomic version guarantee is inferred. Source: [F-037 v1](../features/F-037-mutation-rate-limit-stop.md), D-1–D-4.

## Examples

- **Given** a 429 without `Retry-After` then a 200
  **When** the run ends
  **Then** two attempts were made 1,000 ms apart
- **Given** a 429 with `Retry-After: 31`
  **When** the run ends
  **Then** it is `failed`/`RATE_LIMITED` after one attempt

Pending v2 examples (the preceding examples describe active v1):

- **Given** a permitted rename and a 429 with `Retry-After: 5`
  **When** the target moves into a denied directory during the next 5 seconds
  **Then** the original run has already returned `failed` / `RATE_LIMITED`, attempts 1, status 429, with exactly one intent/outcome pair; a new invocation is `denied` / `ACCESS_DENIED`, attempts 0, with one new `denied` record and no new mutation call. Maps to `TestBR248_v2_AC02_target_moves_into_denied_directory_during_retry_after`.
- **Given** the same 429 with the target still permitted
  **When** the client makes no new invocation through the next 5 seconds
  **Then** no second attempt occurs; only a new explicit invocation performs fresh checks and can succeed with its own intent/outcome pair. Maps to `TestBR248_v2_AC03_unchanged_target_requires_a_new_authorized_invocation`.
- **Given** a valid 429 with `Retry-After: 0` or `Retry-After: 31`
  **When** the outcome is recorded
  **Then** either run returns the same one-attempt `RATE_LIMITED` result without a wait. Maps to `TestBR248_v2_AC01_retry_after_%j_never_schedules_another_attempt`.
